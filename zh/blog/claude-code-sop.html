河蟹 AI 背后的 Claude Code SOP：设计驱动 × 测试闭环 × 多 Agent 协作

一个人、业余时间、6 个核心仓库、68 万行代码。核心不是“让 AI 写代码”，而是设计、测试、多 Agent 协作怎么形成自闭环的一整套研发 SOP。

起因：朋友让我分享点 AI 开发经验

前几天一位在北京的老朋友找我——他是技术负责人，想给团队搞 AI 自动工作流，带着两个具体问题：AI 幻觉怎么压？工作流怎么搭？下面三条主线基本就是对这两个问题的回答。

我这段时间的经验都在项目里跑着，没单独整理成分享材料。让 Claude 把碎片拼成一套文档（也就是文末开源出来的那一套），连同自定义 Skill 和 command 一起打包发过去。那场分享没走"讲一遍"的路子——朋友拉了个微信群做技术交流，问什么答什么，大家边看边实操边问，氛围也轻松，每个问题都有时间答扎实。这其实才是真正的 E2E（端到端）技术交流分享：文档、实操、问题、答疑在一个闭环里走过一遍。

他那边还安排了一位做产品经理的朋友讲产品侧的 Skill 体系。那位朋友的 PRD 写得特别体系化、颗粒度很细。我拿他的 Skill 跑了一下登录模块，直接吐出一份测试用例加一份测试报告——PRD 越细，生成效果越好。产品侧那套体系是人家产品同行的专业，我这边只是拿来用得顺，就不班门弄斧了——真要讲透，得请那位朋友自己出场。

整理出来之后回头看，我自己才意识到——这套"怎么用 Claude Code 做出一个能跑的产品"的用法，之前从没系统写下来过。功能列表谁都会列，但"用法"是另一回事。

核心就三条主线：设计 + 实现、测试闭环、多 Agent 协作——下面依次拆。

这篇文章就是那份文档的精简版。它不讲"Claude Code 有哪 26 个快捷键"，讲的是另一件更硬的事：当你真的要用 Claude Code 做出一个能跑、能测、能演进的产品时，你需要的那套工作流。

先摆数据，不然后面全是废话

  • 约 68 万行代码：分布 Go / TypeScript / Vue / Rust 四种主语言（按六仓库当前 Git 跟踪文件粗略统计）
  • 6 个核心仓库：toolkit → ai-core → hexagon → hexclaw → hexclaw-desktop / hexagon-ui（完整依赖链见架构详解篇）
  • 一个人 · 业余时间：白天正常上班，这套生态全是下班、周末、节假日写的
  • Claude Code 结对开发：每天几十到上百轮结对，大部分代码由 Claude Code 生成，我负责需求输入、方案取舍、审查和最终验收
  • 模型：前面这些活儿是 Claude Opus 4.5 / 4.6 干的，几个月就成了过去式。但不管是刚发的 4.7，还是之后更新的版本——流程是常量，上限随模型水涨船高

数据不是用来炫的。我自己回头看都觉得有点荒谬。

真正反直觉的是：做出来的东西质量，超出我自己的预期——测试覆盖齐全，每个关键决策都有 ADR（架构决策记录），代码审查的严格程度比我过去参与过的不少项目都高，各仓库依赖层级清晰，没有循环引用。

这不是因为 Claude Code 在 2026 年突然变强了——去年就有很多独立开发者在用它，产出质量差着量级。差距不在工具上，在用法上。

顺便一句行业观察——从 Claude Code、Codex、Cursor 和国内代码助手的密集迭代、订阅方案竞争加剧来看，AI 编程已经从尝鲜进入日常工具链。知乎和技术群里最近的高频梗甚至夸张到了这种程度："古法编程，手写代码马上要申遗了，再不申就进博物馆了。"

段子归段子，现实并没这么极端。Stack Overflow 2025 开发者调查里，84% 的开发者使用或计划使用 AI 工具，但 46% 不信任 AI 输出的准确性——普及已成事实，"能不能信"仍然是核心问题。真实共识更接近这个位置：纯手写代码正在从默认动作，变成少数关键场景里的精细活；而要让 AI 写的代码值得信，就得给它设计、测试、审查的闭环。

AI 写代码这件事，2026 年已经不是"要不要用"的问题，是"用得好不好"的问题。工具普及 ≠ 产出质量——同样用 Claude Code，一些人做出了能跑的产品，另一些人只写了几个 demo。

三条主线

顺便对下术语：2026 年前后，业内开始用 Agentic Engineering 来区分更随性的 Vibe coding——两条路径的差异越来越明显。

Vibe coding（Karpathy 提出的说法）是"凭感觉让 AI 写、能跑就行"，适合玩具项目和快速原型；Agentic Engineering 强调的不是"把代码都交给 AI"，而是人类编排 agent、设置质量门禁、验证输出，把 AI 生成代码纳入工程闭环。说到底：AI 可以写代码，不能替你承担工程责任。

这篇文章讲的就是我这套 Agentic Engineering 的具体做法。具体拆开：

① 设计 + 实现：编码前先让 Claude 做方案对比，选定后拆小阶段，每阶段按 TDD 红绿重构。

② 测试闭环：不给 "should pass"、"probably OK" 留口子。跑了测试、拿到证据才算完成。覆盖率高不等于测试有效。

③ 多 Agent 协作：Claude 写代码，Codex 审代码，人类做决策。让两个不同模型交叉审查，避免单一模型的盲区累积成故障。

✏️ ① 设计 + 实现
  • 多方案对比 + ADR 记录
  • 拆小阶段，一次做一个
  • TDD 红 → 绿 → 重构
  • 有测试保护的重构
✅ ② 测试闭环
  • 验证驱动（不接受 should pass）
  • 变更类型 → 测试级别映射
  • grep 完成度自检
  • DevTestOps 流程 Skill
🤖 ③ 多 Agent 协作
  • Claude 写 / Codex 审 / 人类决策
  • 交叉 Code Review
  • 功能闭环评审（对照设计）
  • 历史踩坑教训沉淀为检查项

下面按顺序拆——每条主线配一段真实做法：遇到过什么问题、用什么解决、对应的 prompt / bash 命令。

主线一：设计 + 实现

先讲不做设计的问题

5 个月前我刚上手 Claude Code，第一反应跟大多数人一样："我要做 XXX 功能，你帮我实现。" Claude 秒出 200 行，跑起来也能用。

但用了一段时间后我发现，直接让 AI 写代码有三个具体问题：

1. 架构会悄悄劣化。Claude 每次对话用的是"上下文里最近看到的模式"。随着模块变多，它会把不同风格的代码混在一起。回头看，代码库像是 5 个不同习惯的人写的——因为 Claude 每次对话都是一个"新人"，它不记得你昨天定的规矩。

2. 方案选择被动。Claude 默认给你"一个能跑的方案"，不给对比。但技术选型的价值本来就在对比里——goroutine 还是 channel、REST 还是 WebSocket，不做对比等于没决定。

3. 改动半径不可控。让 Claude "实现一个新功能"，它可能顺手改了好几个其他文件。改得对不对你也不知道，得一个一个看 diff。

正面做法：设计三步

我后来定了一条铁律：

编码之前，必须先过完整的设计阶段。

整个设计阶段默认切到 Plan 模式（Shift+Tab）——Claude 只读不改，专心做分析和方案，不会顺手动你的代码。

三步：

Step 1：把想做什么描述清楚

不要一句话"做个 XXX" 就完事——上下文不够，方案也不会准。我的标准模板：

我要做 XXX 功能。上下文：- 当前系统是 X（技术栈 / 架构 / 关键约束）- 已有的相关代码在 Y- 期望行为是 Z- 非功能要求：性能 / 兼容性 / 并发规模 不要急着出方案。先问我还有什么需要补充的，确认完上下文再开始设计。

"不要急着出方案" 这句关键——默认 Claude 拿到需求就往前冲，加这句它会先把模糊点列出来让你确认。后面的方案才精确。

Step 2：让 Claude 出 2-3 个方案对比

上下文补齐之后才让它出方案。每个方案要能对照着看：

基于上面补全的上下文，出 2-3 个方案。每个方案说清楚：- 核心思路（一句话）- 复杂度 vs 扩展性的权衡- 需要改 / 加哪些模块- 风险点- 这个方案不适合什么场景 不要推荐其中任何一个。我自己选。

最后那句——不是让 Claude 推荐一个你照做，是让 Claude 把选项摆出来，你选。默认 Claude 会倾向推荐一个"看起来最稳"的，加这句堵住这个倾向。

Step 3：选定方案 + 写 ADR

选定后让 Claude 帮你把决策写成 ADR（Architecture Decision Record）：

# ADR-XXX: [决策标题] ## 背景[为什么需要这个决策，上下文是什么] ## 决策[选了什么方案] ## 备选[考虑过哪些其他方案，为什么没选] ## 影响[对代码/架构/团队的影响]

三个月后你自己或接手的人回头看，能立刻明白"当初为什么这么做"——更重要的是，当初评估过的备选方案还在，切换时不用从头调研。

这套三步本质上是业界 Spec-Driven Development（SDD）的精简版——GitHub 开源的 Spec Kit（github.com/github/spec-kit） 会把规划拆得更细，分成多个可审阅阶段。我做产品没那么多仪式，用这三步够了。

实现阶段：从 ADR 到代码

设计完不是直接"一把梭"让 Claude 把整个方案实现出来。三个做法：

做法 1：拆小阶段，一次只做一个

ADR 选定的方案拆成"能独立上线的小阶段"——每个阶段代码量可控、可独立提测、有问题回滚成本低。一次实现整个方案的后果是：diff 太大没人能审、出问题不知道退到哪、前期假设错了后面全白写。

让 Claude 先把拆分方案列出来，你确认后一个一个做：

基于 ADR-023 的选定方案，把实现拆成可独立上线的阶段： 要求：1. 每个阶段独立可提测（不依赖未完成的阶段）2. 每个阶段有明确验收标准3. 排出执行顺序（优先级最高的先做）4. 标注每个阶段的风险点 先列出拆分结果，等我确认后再开始第一个阶段。

做法 2：TDD 红 → 绿 → 重构

具体任务适合 TDD 的，用下面这个提示词：

用 TDD 方式实现服务熔断逻辑： 第一步（红）：先写测试，覆盖以下场景  - 连续 3 次失败触发熔断  - 熔断期间所有请求直接拒绝  - 熔断 60s 后进入半开状态  - 半开成功 1 次恢复 / 失败则重新熔断  - 并发安全 第二步（绿）：写最少代码让所有测试通过 第三步（重构）：优化代码结构，确保测试仍然全绿 每一步都要实际运行测试并展示结果。

但 TDD 不是银弹——得看场景：

  • 适合 TDD：核心纯逻辑 / 状态机 / 算法 / Bug 修复 / 接口契约
  • 不适合 TDD：探索性开发（需求不明）/ 前端交互（行为难用单元测试描述）/ 第三方集成（依赖外部行为）/ 一次性脚本

不适合 TDD 的，先 spike（快速原型）跑通再补测试，别硬上。

做法 3：有测试保护的重构

改已有代码（不是写新代码）时，流程严格：

我要重构 adaptor_factory.go 里的大 switch-case（30+ case）。 按以下步骤执行：1. 先跑现有测试，确认全绿（这是 baseline）2. 分析 switch 的模式，提取公共行为3. 设计策略模式/注册表模式的替代4. 逐步替换——每步改完跑一次测试5. 最终确认测试全绿 + 行为不变 约束：不改变外部 API 行为。任何一步测试不绿，立即回滚那一步。

关键是"每步改完跑一次测试"——不是一次改完再跑。一次改完跑出来红的，你根本不知道是哪一步改错的。

这套"三步设计 + 三个实现做法"跑下来看起来花时间——实际对比就知道：设计阶段多花的 1 小时，后续实现和演进阶段能省下 10 倍。方案对比过、决策有 ADR 记着，备选永远在，切换成本低；跳过这步的代价是：每次改动半径不可控，遇到问题只能重新调研。

主线二：测试闭环

先讲 Claude 写测试的坑

你说"给 XXX 函数写单元测试"，Claude 30 秒给你一套。但它有个致命问题：会为了"覆盖到代码"而写，不是为了"验证行为"而写。

典型假阳性：

func TestCalculateDiscount(t *testing.T) {    result := CalculateDiscount(100, 0.1)    // 没有 assert，只是调用了函数}

或者：

func TestParseConfig(t *testing.T) {    _, err := ParseConfig("valid.yaml")    assert.NoError(t, err)    // 只测了 happy path，没测任何异常}

这种测试覆盖率会很高，但真有 bug 根本测不出来。我自己吃过亏——某次覆盖率 90%+，但某个关键路径的边界条件没测到，上线后线上直接崩。

正面做法：验证驱动 + 完成度自检

铁律 1：验证驱动（Anthropic 官方最佳实践（code.claude.com/docs/en/best-practices）里反复强调的一条）

给 Claude 验证手段是高杠杆率做法——Claude 能自我验证时，输出质量会大幅提升。

四种给验证的方式：

重构 auth 中间件，改成 JWT。改完后运行现有测试套件，修复所有失败用例后再结束。

（测试作为验证）

修改登录页布局。改完后截图给我，确认没有 UI 回归。

（截图作为验证）

请实际运行验证，而不是假设它能工作。

（拒绝"我认为能运行"）

仔细审查这些改动，确认没有遗漏后再提交。

（自我审查）

关键是不接受 "should pass" 和 "probably OK"——跑了测试、拿到证据才算。

铁律 2：变更类型 → 测试级别映射

不同变更，对应不同测试覆盖深度：

变更类型必须完成建议补充
纯逻辑调整单元 + 模块 + 回归边界值 + 异常路径
接口改动+ API 测试 + 兼容性检查错误码 + 鉴权
跨模块改动+ 集成测试 + 数据一致性超时重试
核心链路改动+ E2E + 专项测试上线验证清单
高风险改动+ 性能基准 + 回滚演练异常场景演练

把这个表贴在项目的 CLAUDE.md 里——Claude 每次写测试都会自动对照。

铁律 3：完成度自检

声称"XXX 已修复"之后，必须运行 grep 确认没有残留。

# 声称"ctx 断层已修"之后，必须跑grep -c 'context.Background()' <所有相关文件> # 结果必须为 0，或全是合法用法，不能有漏网的

"我觉得改完了"不算证据，grep -c 的结果才算。

完成度自检的本质——不让 AI 的"感觉已经修完了"代替证据。具体每个项目什么覆盖率、漏几个 case 每次不一样；但"声明完成 → grep 扫残留 → 发现遗漏就补"这个回路必须有。

再加一层：用 Hooks 把检查自动化

完成度自检靠你每次手动想起来跑 grep，总会漏。Claude Code 的 Hooks 机制能把这些检查写成 shell 脚本，在特定事件自动触发——这是让 AI 代你跑也不翻车的关键。

最实用的两个：

Pre-commit hook——Claude 要提交前拦截，防敏感文件 leak：

# ~/.claude/hooks/pre-commit.shif git diff --cached --name-only | grep -E '\.(env|pem|key|secret)$'; then  echo "❌ 阻止：检测到敏感文件"  exit 1fi

Post-edit hook——Claude 改完文件后自动跑 lint / 编译 / 测试：

# ~/.claude/hooks/post-edit.shfor f in "$@"; do  case "$f" in    *.go) go vet "$f" || exit 1 ;;    *.ts) npx tsc --noEmit "$f" || exit 1 ;;    *.py) ruff check "$f" || exit 1 ;;  esacdone

把"检查"从"我要记得做"变成"自动做"——这是让 Claude Code 能 unattended 运行的核心。我日常开发环境挂了 6-7 个 hook，覆盖敏感文件、lint、编译、关键测试。Claude 没跑通这些钩子，改动根本进不了仓库。

延伸：完整的 DevTestOps 流程 Skill

上面讲的三条铁律，只是"测试闭环"里最常用的部分。完整版本我做成了一个 Skill，名字就叫 devtestops——装进 Claude Code 的 ~/.claude/skills/，整个 pipeline 能自动触发。

里面包含：

  • 7 阶段交付流程：需求澄清 → 方案与用例准备 → 基础质量验证 → 主链路验证 → 专项与性能 → 提测与回归 → 上线与观察
  • 8 类专项测试触发规则：E2E / 接口 API / 权限安全 / 并发幂等 / 数据一致性 / 异步任务队列 / 配置兼容性 / 回滚可观测
  • 提测准入基线：按变更类型算出的最低质量门槛

相比上面那张"变更类型 → 测试级别"表，这套 Skill 能让 Claude 在跑任何改动时自动识别该触发哪些专项检查，不用你每次提醒。

主线三：多 Agent 协作

反面教材：让一个 AI 干所有事

"Claude 很强，让它一个人把设计 / 编码 / 审查 / 测试都干了。"

听起来很高效。

实际上是反模式。

原因有三：

1. 同一个模型有系统性盲区。

Claude 和 Codex 背后的模型体系、训练数据、推理偏好不同。

让 Claude 审查自己写的代码——它会漏掉自己风格里的问题。

人也有这毛病，审自己代码效率最低。

2. 一问一答模式不适合审查。

审查需要"对抗性思维"——主动找问题，不是顺着写的思路走。

但 Claude 在同一段对话里已经跟你"达成了共识"，切审查模式会倾向于维持共识。

3. 单模型没有交叉验证。

好的审查是"两个独立角度撞出盲区"。

一个模型的两轮对话，不是独立角度。

正面做法：Claude + Codex + 人类，三角分工

明确分工：

角色负责来源
Claude方案设计、架构分析、编码实现、TDDClaude Code 主会话
CodexCode Review、测试盲区补充、设计文档评审Claude Code 里的 Codex 插件
人类需求输入、方案决策、最终确认你

不用开两个终端。OpenAI 在 GitHub 上提供了 codex-plugin-cc（github.com/openai/codex-plugin-cc）插件，直接装进 Claude Code 就能在主会话里用 Codex。

安装一次：

/plugin marketplace add openai/codex-plugin-cc/plugin install codex@openai-codex/reload-plugins/codex:setup

装完整个协作流程就是四个斜杠命令。前提：Node.js 18.18+、已登录 ChatGPT 订阅或配好 Codex API key。

步骤 A：Claude 写完 → /codex:review 让 Codex 审

# 在 Claude Code 主会话里，写完代码后直接：/codex:review --base main # 如果要更狠的对抗性审查（Codex 会质疑架构和实现选择）：/codex:adversarial-review --base main challenge whether this is the right design

Codex 独立跑审查，不走 Claude 的上下文——两个模型从零开始看 diff，真正做到"独立审查"。

步骤 B：审查意见喂回 Claude 逐条回应

Codex 审查报告出来后，在同一个 Claude Code 会话里：

以下是 Codex 的审查意见。请逐条回应：接受并修复 / 用技术证据反驳 / 标记为待讨论。不要表演性认同——如果 reviewer 错了要用技术证据说明为什么。 对属于 bug / 逻辑错误类的意见，修复时先写测试复现问题（红），修完让测试通过（绿）——用"修复前失败 / 修复后通过"的证据替代"我改完了"。架构建议 / 命名风格 / 可读性类不用强行写测试。 [审查意见自动在上下文里，不用复制粘贴]

关键是最后那句——"不要表演性认同"。Claude 默认客气，不加这句它会把 Codex 说的大部分都认下来，对抗审查就失效了。

步骤 C：让 Codex 补测试盲区

# 在 Claude Code 主会话里，让 Codex 补测试盲区@codex 请阅读 src/xxx.go 和已有测试，找测试盲区：- 哪些边界情况没覆盖？- 哪些并发场景没测？- 哪些错误路径没验证？

这一步常抓到 Claude 自己没想到的测试场景——尤其是并发竞态和错误路径。

步骤 D：最后一步——对照设计文档做功能闭环评审

代码能跑 ≠ 需求都实现了。这是整套协作的最后一道防线，防的是"技术代码都对，但产品需求根本没做完"。

# 在 Claude Code 主会话里对照设计文档和 git diff，逐条检查： ## A. 需求覆盖率每条功能需求标注：- ✅ 已实现（给出代码位置）- ❌ 未实现（遗漏）- ⚠️ 部分实现（说明缺什么） ## B. 流程闭环每条业务流程追踪完整链路：入口 → 处理 → 存储 → 响应 → 前端展示检查"代码存在但流程断裂"：写了数据但没人读 / 状态变了但没通知 / 接口有了但前端没调。 ## C. 异常场景覆盖超时 / 并发 / 重复 / 部分失败，每个都要有对应代码。 ## D. 非功能需求性能是否满足？安全约束是否落地？监控指标是否埋点？

然后让 Codex 独立做一遍同样检查。

两份报告对比：

  • 两者都发现 → 高优先级修复
  • 只有一方发现 → 验证是否真实存在
  • 两者结论矛盾 → 列出争议点，人类决策

"高优先级修复" 时直接套用步骤 B 的流程——bug 类意见先写测试复现（红），修完验证通过（绿）；非 bug 类（需求遗漏 / 流程断裂 / 非功能欠缺）按设计文档原意补齐。不要让"闭环评审"退化成口头说"我补一下"就过——评审发现的事项必须留可验证的证据。

先走一遍：人类给需求上下文 → Claude 出方案对比 + ADR → Claude TDD 实现 → Codex 独立审查。审查有问题走下半圈：Codex 补测试盲区 → Claude 修 bug → Claude + Codex 做闭环评审 → 人类确认上线。

关键是两行之间那个回路——任何一步出了问题都能退回上一步重来，不是一条线的流水线。比如 Codex 审出一个递归未修的降级分支，就退回 TDD 环节补测试、再重修。

实战：把 SOP 封装成斜杠命令

上面这套 pipeline 我封装成了自定义命令。

一个斜杠即可触发。

两个核心命令：

/review-go：Go 后端深度审查

对当前分支相对 main 的全部变更，执行深度审查： 1. 机械扫描（前置，不可跳）：   - context.Background 残留   - http.NewRequest 未传 ctx   - io.ReadAll 无 LimitReader   - per-call 创建 Transport/Client 2. 递归审查：   - 追到叶子节点（HTTP / DB / 文件 IO）   - 覆盖所有分支（成功 / 失败 / 降级 / 重试） 3. 完成度自检：   - grep 确认修复无残留   - go build 确认接口适配 4. 历史踩坑教训检查（从反模式列表里扫）

/review-fullstack：全栈审查

在 /review-go 基础上，增加前后端契约、功能闭环、跨仓库生态链影响的检查。

最值钱的部分：历史踩坑教训

整套 SOP 最值钱的东西，不是那些命令模板。

是每次翻车后沉淀下来的"历史踩坑教训"——作为 Pipeline 的强制检查项。

每次发现一个 AI 审查没抓住的 bug，就把它抽象成"反模式"，加进 Pipeline。

举个真实案例——某次修 ctx 断层：我让 Claude 把一个外层函数的 context.Background() 改成透传的 ctx，它改完、跑了测试、声明完成。

过 /codex:review 审一遍，Codex 甩回来：外层 ctx 是修好了，但同文件里 if err != nil 的降级分支仍在调 Background；而且同一模块另外两个 helper 也在偷偷 context.Background() 起新的 ctx。

回去一看——确实。Claude 当时的"已完成"只覆盖了改动半径内的那一个入口，没递归到整条调用链。

修完之后我把"只追成功路径，不追降级分支"抽成 /review-go 里的 grep 检查项。从那以后，同类 bug 再没漏网过。

这就是"历史踩坑教训"机制的价值——单次故障不怕，怕的是同类故障重复发生。把每次翻车变成 Pipeline 里的强制检查项，下次 Claude 或 Codex 就会自动扫一遍。

下面是我这 5 个月实际加进去的几条：

  1. 只审修改的函数，不递归审子函数 — 修了外层 ctx，但它调的 helper 仍用 context.Background()
  2. 只追成功路径，不追降级分支 — 正常路径 ctx 修好了，但 if err != nil 后的降级路径仍用 Background
  3. 接口签名改了但没检查所有实现 — dev 上有 main 没有的实现文件，合并后编译失败
  4. 声称修完但没 grep 验证残留 — "ctx 断层已修"，但同文件还有多个 helper 用 Background
  5. 邻居函数有相同问题没扫到 — 修了一个函数的 per-call Transport，同文件其他函数也在 per-call 创建

这个清单会越用越长——每加一条，后面同类 bug 的漏检率降低一档。这是 Pipeline 的复利：每次翻车都会沉淀成下次的强制检查项。

一个术语澄清

在 Claude Code 语境里，很多人说"multi-agent"会先想到内置的 subagent 机制——同一模型的多个实例并行调研；更广义的 multi-agent 则包括多个模型、多个工具链、多个上下文窗口之间的协作。一个常被引用的数据来自 Anthropic 官方博客《How we built our multi-agent research system》（anthropic.com/engineering/built-multi-agent-research-system）：2025 年 Opus 4 作 lead + Sonnet 4 作 subagent 的组合，在内部 research 评测上比单 Opus 4 高 90.2%（注意：这是 research eval，不是代码评审 eval，不能直接外推到软件开发场景）。

本文讲的"多 Agent 协作"是 跨模型（Claude × Codex）这一种，主要为了消除单一模型的盲区。

两者不冲突，实际做重要功能时我会都用：Claude 的 subagent 并行读代码做调研 → Claude 出方案和实现 → Codex 交叉审。内置 subagent 的具体用法下一篇单讲。

AI 做不到什么

讲完三条主线，补一段边界：这段时间下来我很清楚，AI 再强，有 3 件事做不到。

1. 架构决策。

Claude 能给你列方案，但选哪个必须人类定。

因为架构决策需要对"业务未来方向"的直觉——这件事 AI 没数据。

2. 跨系统一致性判断。

单仓库内 Claude 跑得很好。

但"这 3 个仓库之间的接口约定是否合理"、"这次改动对生态链其他仓库有什么影响"——

AI 的上下文窗口装不下这些。

必须人类在脑子里建立全局地图。

3. 产品体验直觉。

"这个交互用户会喜欢吗"、"这个错误提示会不会吓到用户"、"这个功能该不该默认开启"——

这些问题 AI 没有真实用户反馈，只能给你"一般做法"。

所以 AI 放大的是你已经有的判断力。判断力本身还得你自己有。

关于 Opus 4.7：SOP 要不要改？

Claude Opus 4.7（anthropic.com/news/claude-opus-4-7） 刚发，官方宣称在编码、长任务、指令遵循这几个维度对前一代有提升，问得最多的一个问题是：这套 SOP 在 4.7 上要不要改？

答案：主干不用推倒重来，但提示词、评审门禁、测试 harness 要重新跑一遍回归。

原因是：模型升级不会让"要不要做设计、要不要跑测试、要不要交叉审查"这些问题失效——这三条是工作流层面的判断，跟模型能力无关。但模型更强之后，同一段提示词和旧的验证门槛可能不再匹配：

  • 提示词的措辞：老版本能容忍的模糊指令，4.7 可能更按字面执行，范围和输出格式都得更精确
  • 评审门禁：如果你之前的 /review-go 严格度是照 4.6 的行为微调过的，换 4.7 之后得重新标定什么算 noise、什么算真问题
  • 测试 harness 的期望值：一些"通常会失败所以 tolerant"的 case，在 4.7 上可能变成稳定通过——该收紧的就收紧

我正在用 4.7 把整套 SOP 重跑一遍做回归验证，重点盯这几项：Plan 模式的架构分析、长上下文一次吞整个仓库、交叉审查时的对抗性。数据和 case 拿到后下一篇单独写。
