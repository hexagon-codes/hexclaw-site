بىر ئادەم، ئىشتىن سىرتقى ۋاقىت، 6 يادرولۇق ئامبار، 680 مىڭ قۇر كود. يادرولۇق مەسىلە «AI غا كود يازدۇرۇش» ئەمەس؛ لايىھە، سىناق ۋە كۆپ Agent ھەمكارلىقىنى ئۆزلۈكىدىن تاماملىنىدىغان ئېچىش SOP سىغا ئايلاندۇرۇش.

باشلىنىشى: بىر دوستۇم AI ئېچىش تەجرىبىسىنى ئورتاقلىشىشنى سورىدى

بىر نەچچە كۈن ئىلگىرى بېيجىڭدىكى كونا دوستۇم ئالاقىلەشتى. ئۇ تېخنىكا مەسئۇلى، گۇرۇپپىسىغا AI ئاپتوماتىك خىزمەت ئېقىمى قۇرماقچى بولۇپ، ئىككى كونكرېت سوئال سورىدى:AI نىڭ توقۇشىنى قانداق بېسىمىز؟ خىزمەت ئېقىمىنى قانداق قۇرىمىز؟تۆۋەندىكى ئۈچ ئاساسىي يول مۇشۇ ئىككى سوئالنىڭ جاۋابى.

بۇ مەزگىلدىكى تەجرىبىلىرىم تۈردە ئىشلىۋاتاتتى، ئايرىم تونۇشتۇرۇش ماتېرىيالى قىلماپتىمەن. Claude قا پارچىلارنى بىر يۈرۈش ھۆججەتكە يىغدۇردۇم (ماقالە ئاخىرىدا ئوچۇق مەنبە قىلىنغان شۇ يۈرۈشلۈك)، خاس Skill ۋە command لار بىلەن بوغچىلاپ ئەۋەتتىم. ئۇچرىشىش بىر قېتىملىق «سۆزلەپ بېرىش» ئەمەس ئىدى: دوستۇم WeChat توپى قۇرۇپ تېخنىكا ئالماشتۇرۇش قىلدى؛ سوئال كەلسە جاۋاب بەردۇق، ھەممە كۆرۈپ، ئەمەلىي ئىشلىتىپ، سوراپ تۇردى. كەيپىيات ئازادە، ھەر سوئالغا پۇختا جاۋاب بېرىشكە ۋاقىت بار ئىدى. ھەقىقىي E2E تېخنىكا ئالماشتۇرۇش دېگەن مۇشۇ: ھۆججەت، ئەمەلىي مەشغۇلات، سوئال ۋە جاۋاب بىر ئايلىنىشتا ئۆتىدۇ.

ئۇ يەنە مەھسۇلات باشقۇرغۇچى دوستىنى مەھسۇلات تەرەپ Skill سىستېمىسىنى سۆزلەشكە چاقىردى. ئۇ دوستنىڭ PRD سى ناھايىتى سىستېمىلىق ۋە ئىنچىكە. ئۇنىڭ Skill ى بىلەن كىرىش مودۇلىنى ئىجرا قىلىپ كۆردۈم، بىۋاسىتە بىر سىناق دېلوسى ۋە بىر دوكلات چىقاردى —PRD قانچە ئىنچىكە بولسا ھاسىل قىلىش شۇنچە ياخشى. مەھسۇلات تەرەپ سىستېمىسى ئۇ كەسىپدىشىمنىڭ كەسپى؛ مەن پەقەت قولايلىق ئىشلەتتىم، ئۆزۈمنى بىلىملىكتەك كۆرسەتمەيمەن. تولۇق چۈشەندۈرۈش ئۈچۈن ئۇ دوست ئۆزى سۆزلىشى كېرەك.

يىغىپ بولغاندىن كېيىن ئۆزۈممۇ بايقىدىم: «Claude Code بىلەن ئىجرا بولىدىغان مەھسۇلات ياساش» ئۇسۇلىنى بۇرۇن سىستېمىلىق يېزىپ باقماپتىمەن. ئىقتىدار تىزىملىكىنى ھەممە تىزالايدۇ، «قانداق ئىشلىتىش» باشقا ئىش.

يادرولۇق ئۈچ يول:لايىھە + ئىجرا، سىناقنى تاماملاش، كۆپ Agent ھەمكارلىقى— تۆۋەندە رەت بويىچە ئاچىمىز.

بۇ ماقالە شۇ ھۆججەتنىڭ قىسقارتىلغان نۇسخىسى. «Claude Code نىڭ 26 تېز كۇنۇپكىسى»نى ئەمەس، تېخىمۇ ئەمەلىي بىر ئىشنى سۆزلەيدۇ: ئىجرا بولىدىغان، سىنىغىلى بولىدىغان، تەرەققىي قىلدۇرغىلى بولىدىغان مەھسۇلاتنى ھەقىقىي ياسىغاندا قانداق خىزمەت ئېقىمى كېرەك؟

  • مودېل: يۇقىرىقى ئىشلارنى Claude Opus 4.5 / 4.6 قىلدى؛ بىر نەچچە ئايدىلا ئۆتمۈش بولدى. يېڭى ئېلان قىلىنغان 4.7 بولسۇن، كېيىنكى نۇسخىلار بولسۇن، ئېقىم تۇراقلىق، يۇقىرى چەك مودېل بىلەن ئۆسىدۇ

بۇ سانلار ماختىنىش ئۈچۈن ئەمەس. ئۆزۈممۇ قايتا قارىسام سەل غەلىتە ھېس قىلىمەن.

ھەقىقىي كۈتۈلمىگىنى:چىققان نەرسىنىڭ سۈپىتى ئۆز مۆلچەرىمدىن ئېشىپ كەتتى— سىناق قاپلىشى تولۇق، ھەر مۇھىم قارارنىڭ ADR ى (قۇرۇلما قارار خاتىرىسى) بار، كود تەكشۈرۈش قاتتىقلىقى مەن قاتناشقان نۇرغۇن تۈردىن يۇقىرى؛ ئامبار تايىنىش قەۋىتى ئېنىق، ئايلانما تايىنىش يوق.

بۇ Claude Code نىڭ 2026-يىلى تۇيۇقسىز كۈچەيگەنلىكىدىن ئەمەس. ئۆتكەن يىلىمۇ نۇرغۇن مۇستەقىل ئاچقۇچى ئىشلىتەتتى، مەھسۇلات سۈپىتى قاتمۇقات پەرق قىلاتتى. پەرق قورالدا ئەمەس، ئىشلىتىش ئۇسۇلىدا.

بىر ساھە كۆزىتىشىمۇ بار: Claude Code، Codex، Cursor ۋە دۆلەت ئىچىدىكى كود ياردەمچىلىرىنىڭ تېز يېڭىلىنىشى، مۇشتەرىلىك پىلانلىرىنىڭ رىقابىتىدىن قارىغاندا،AI بىلەن كود يېزىش يېڭىلىق سىناشتىن كۈندىلىك قورال زەنجىرىگە كىردى. Zhihu ۋە تېخنىكا توپلىرىدىكى يېقىنقى چاقچاق ھەتتا مۇنداق دەيدۇ:«قەدىمىي ئۇسۇلدا قولدا كود يېزىش يېقىندا مەدەنىي مىراسقا ئىلتىماس قىلىدۇ؛ ئالدىرىمىسا مۇزېيغا كىرىپ كېتىدۇ.»

چاقچاق ئۆز يولىغا، رېئاللىق ئۇنچە چېكىدىن ئاشمىغان. Stack Overflow 2025 ئاچقۇچىلار تەكشۈرۈشىدە،84% ئاچقۇچى AI قورالى ئىشلىتىدۇ ياكى ئىشلىتىشنى پىلانلايدۇ، ئەمما 46% AI چىقىرىلمىسىنىڭ توغرىلىقىغا ئىشەنمەيدۇ— ئومۇملىشىش پاكىت، «ئىشەنسەك بولامدۇ» يەنىلا يادرولۇق سوئال. ھەقىقىي ئورتاق قاراش شۇنىڭغا يېقىن: پۈتۈنلەي قولدا يېزىش سۈكۈتتىكى ھەرىكەتتىن ئاز سانلىق مۇھىم ئەھۋالدىكى نازۇك ئىشقا ئايلىنىۋاتىدۇ؛ AI كودى ئىشەنچلىك بولسۇن دېسەك لايىھە، سىناق ۋە تەكشۈرۈش ئايلىنىشى كېرەك.

2026-يىلى سوئال «AI نى ئىشلىتەمدۇق» ئەمەس، «ياخشى ئىشلىتەمدۇق». قورال ئومۇملىشىشى ≠ مەھسۇلات سۈپىتى. ئوخشاش Claude Code بىلەن بەزىلەر ھەقىقىي مەھسۇلات ياسىدى، بەزىلەر بىر نەچچە demo لا يازدى.

ئۈچ ئاساسىي يول

ئاتالغۇنىمۇ توغرىلايلى: 2026-يىلى ئەتراپىدا ساھە Agentic Engineering دېگەننى تېخىمۇ ئەركىن Vibe coding تىن ئايرىشقا باشلىدى؛ ئىككى يولنىڭ پەرقى روشەنلىشىۋاتىدۇ.

Vibe coding (Karpathy ئوتتۇرىغا قويغان) «ھېسقا تايىنىپ AI غا يازدۇرۇش، ئىجرا بولسىلا بولدى»؛ ئويۇنچۇق تۈر ۋە تېز ئەندىزىگە ماس. Agentic Engineering نىڭ تەكىتلىگىنى «كودنىڭ ھەممىسىنى AI غا بېرىش» ئەمەس، بەلكىئادەمنىڭ agent لارنى ئورۇنلاشتۇرۇشى، سۈپەت دەرۋازىسى قويۇشى، چىقىرىلمىنى دەلىللىشى، AI ھاسىل قىلغان كودنى ئىنژېنېرلىق ئايلىنىشىغا كىرگۈزۈش. تۈپ مەنىسى:AI كود يازالايدۇ، ئەمما ئىنژېنېرلىق مەسئۇلىيىتىڭىزنى كۆتۈرەلمەيدۇ。

بۇ ماقالە مېنىڭ Agentic Engineering ئىجرايىمنى سۆزلەيدۇ. كونكرېت:

① لايىھە + ئىجرا: كودتىن بۇرۇن Claude قا ھەل قىلىش چارىلىرىنى سېلىشتۇردۇرۇش، تاللىغاندىن كېيىن كىچىك باسقۇچقا بۆلۈپ، ھەر باسقۇچتا TDD قىزىل-يېشىل-قايتا قۇرۇش.

② سىناقنى تاماملاش: «should pass»، «probably OK» دېگەن بوشلۇق قالدۇرماسلىق. سىناق ئىجرا بولغان، ئىسپات ئېلىنغاندىلا تامام. يۇقىرى قاپلاش سىنىقى ئۈنۈملۈك دېگەنلىك ئەمەس.

③ كۆپ Agent ھەمكارلىقى: Claude كود يازىدۇ، Codex تەكشۈرىدۇ، ئادەم قارار قىلىدۇ. ئىككى ئوخشىمىغان مودېل ئۆزئارا تەكشۈرۈپ، بىر مودېلنىڭ كۆرەلمىگەن نۇقتىسىنىڭ خاتالىققا يىغىلىشىنى توسىدۇ.

  • كىچىك باسقۇچ، بىر قېتىمدا بىرلا ئىش
  • TDD قىزىل → يېشىل → قايتا قۇرۇش
  • سىناق قوغدىغان قايتا قۇرۇش

  • ئۆزگىرىش تۈرى → سىناق دەرىجىسى خەرىتىسى
  • grep بىلەن تاماملىقنى تەكشۈرۈش
  • DevTestOps ئېقىم Skill ى

تۆۋەندە رەت بويىچە ئاچىمىز؛ ھەر يولغا ھەقىقىي ئۇسۇل، ئۇچرىغان مەسىلە، ھەل قىلىش ۋە ماس prompt / bash بۇيرۇقى بېرىلىدۇ.

بىرىنچى يول: لايىھە + ئىجرا

ئالدى بىلەن لايىھەسىز ئىشنىڭ مەسىلىسى

5 ئاي بۇرۇن Claude Code نى يېڭى باشلىغاندا تۇنجى ئويۇم كۆپچىلىككە ئوخشاش: «XXX ئىقتىدارىنى قىلاي، ئىجرا قىلىپ بەر». Claude دەرھال 200 قۇر چىقىرىدۇ، ئىجرا قىلسىمۇ ئىشلىيدۇ.

ئەمما بىر مەزگىلدىن كېيىن AI غا بىۋاسىتە كود يازدۇرۇشنىڭ ئۈچ كونكرېت مەسىلىسىنى بايقىدىم:

1. قۇرۇلما جىمجىت ناچارلىشىدۇ. Claude ھەر سۆھبەتتە «كونتېكىستتا يېقىندا كۆرگەن ئەندىزە»نى ئىشلىتىدۇ. مودۇل كۆپەيگەندە ھەر خىل ئۇسلۇبنى ئارىلاشتۇرىدۇ. قايتا قارىسىڭىز كود ئامبىرىنى ئادىتى باشقا 5 ئادەم يازغاندەك؛ چۈنكى ھەر سۆھبەتتىكى Claude بىر «يېڭى كەلگەن»، تۈنۈگۈنكى قائىدىنى ئەسلىيەلمەيدۇ.

2. چارە تاللاش پاسسىپ بولىدۇ. Claude سۈكۈتتە «ئىجرا بولىدىغان بىر چارە» بېرىدۇ، سېلىشتۇرما بەرمەيدۇ. ئەمما تېخنىكا تاللاشنىڭ قىممىتى سېلىشتۇرۇشتا: goroutine مۇ channel مۇ، REST مۇ WebSocket مۇ؛ سېلىشتۇرمىسا قارار قىلغانلىق ئەمەس.

3. ئۆزگىرىش دائىرىسى كونترولسىز. «يېڭى ئىقتىدار ئىجرا قىل» دېسىڭىز، Claude باشقا بىر نەچچە ھۆججەتنىمۇ قوشۇمچە ئۆزگەرتىشى مۇمكىن. توغرىمۇ يوق بىلمەيسىز، diff نى بىرمۇبىر ئوقۇش كېرەك.

توغرا ئۇسۇل: لايىھەنىڭ ئۈچ قەدىمى

كېيىن قاتتىق بىر قائىدە بېكىتتىم:

كود يېزىشتىن بۇرۇن تولۇق لايىھە باسقۇچىدىن ئۆتۈش شەرت.

پۈتۈن لايىھە باسقۇچىدا سۈكۈتتە Plan ھالىتىگە（Shift+Tab) ئۆتىمىز؛ Claude پەقەت ئوقۇيدۇ، ئۆزگەرتمەيدۇ، تەھلىل ۋە چارە بىلەنلا شۇغۇللىنىدۇ، كودىڭىزغا قوشۇمچە تەگمەيدۇ.

ئۈچ قەدەم:

Step 1: نېمە قىلماقچى بولغانلىقىڭىزنى ئېنىق ئېيتىڭ

بىر جۈملە «XXX نى قىل» بىلەنلا تۈگىتىۋەتمەڭ؛ كونتېكىست كەم بولسا چارىمۇ توغرا بولمايدۇ. مېنىڭ ئۆلچەملىك قېلىپىم:

مەن XXX ئىقتىدارىنى قىلاي. كونتېكىست:- ھازىرقى سىستېما X (تېخنىكا stack ى / قۇرۇلما / مۇھىم چەكلىمە)- ئالاقىدار كود Y دە- كۈتۈلگەن ھەرىكەت Z- ئىقتىدارسىز تەلەپ: ئۈنۈم / ماسلىشىش / پاراللېللىق كۆلىمى چارە چىقىرىشقا ئالدىرىما. ئالدى بىلەن يەنە نېمە تولدۇرۇش لازىملىقىنى مەندىن سورا،كونتېكىست جەزملەشكەندىن كېيىن لايىھەنى باشلا.

«چارە چىقىرىشقا ئالدىرىما» مۇھىم؛ Claude سۈكۈتتە تەلەپنى ئېلىپلا ئالغا چاپىدۇ. بۇ جۈملە ئۇنى مۈجمەل نۇقتىلارنى ئاۋۋال تىزىپ جەزملەشتۈرىدىغان قىلىدۇ، كېيىنكى چارە ئېنىق بولىدۇ.

Step 2: Claude تىن 2–3 چارە سېلىشتۇرمىسى سوراڭ

كونتېكىست تولغاندىن كېيىنلا چارە سوراڭ. ھەر چارەنى سېلىشتۇرۇپ كۆرگىلى بولسۇن:

يۇقىرىدا تولدۇرۇلغان كونتېكىستقا ئاساسەن 2–3 چارە چىقار. ھەر بىرىدە:- يادرولۇق ئوي (بىر جۈملە)- مۇرەككەپلىك بىلەن كېڭەيتىلىشچانلىق ئارىسىدىكى تاللاش- قايسى مودۇل ئۆزگىرىدۇ / قوشۇلىدۇ- خەتەر نۇقتىسى- قايسى ئەھۋالغا ماس ئەمەس ھېچقايسىسىنى تەۋسىيە قىلما، ئۆزۈم تاللايمەن.

ئاخىرقى جۈملە —Claude بىرنى تەۋسىيە قىلىپ سىزنى ئەگىشىشكە ئەمەس، تاللاشلارنى قويۇپ سىزنى تاللاشقا چاقىرىدۇ. Claude سۈكۈتتە «ئەڭ مۇقىم كۆرۈنگەن»نى تەۋسىيە قىلىدۇ؛ بۇ جۈملە شۇ مايىللىقنى توسىدۇ.

Step 3: چارەنى تاللاپ ADR يېزىڭ

تاللىغاندىن كېيىن Claude قا قارارنى ADR (Architecture Decision Record) قىلىپ يازدۇرۇڭ:

# ADR-XXX: [قارار ماۋزۇسى] ## ئارقا كۆرۈنۈش[نېمىشقا بۇ قارار كېرەك، كونتېكىست نېمە] ## قارار[قايسى چارە تاللاندى] ## باشقا تاللاشلار[قايسىلار ئويلاشتى، نېمىشقا تاللانمىدى] ## تەسىر[كود / قۇرۇلما / گۇرۇپپىغا تەسىرى]

ئۈچ ئايدىن كېيىن ئۆزىڭىز ياكى ئۆتكۈزۈۋالغۇچى قايتا قاراپ، «نېمىشقا شۇنداق قىلغان»نى دەرھال چۈشىنىدۇ. تېخىمۇ مۇھىمى باھالانغان باشقا چارىلەر ساقلىنىدۇ، ئالماشتۇرغاندا باشتىن تەتقىق قىلىش ھاجەتسىز.

بۇ ئۈچ قەدەم ئەمەلىيەتتە ساھەدىكى Spec-Driven Development（SDD）نىڭ ئاددىي نۇسخىسى؛ GitHub دىكى ئوچۇق مەنبە Spec Kit（github.com/github/spec-kit） پىلاننى تېخىمۇ ئىنچىكە، كۆرۈپ چىققىلى بولىدىغان كۆپ باسقۇچقا بۆلىدۇ. مەھسۇلات ياسىغاندا ئۇنچە مۇراسىم كېرەك ئەمەس، بۇ ئۈچ قەدەم يېتىدۇ.

ئىجرا باسقۇچى: ADR دىن كودقا

لايىھە پۈتسىلا Claude قا پۈتۈن چارەنى بىراقلا ئىجرا قىلدۇرمايمىز. ئۈچ ئۇسۇل بار:

ئۇسۇل 1: كىچىك باسقۇچقا بۆلۈپ، بىر قېتىمدا بىرلا ئىش

ADR تاللىغان چارەنى «ئايرىم تورغا چىقارغىلى بولىدىغان كىچىك باسقۇچ»قا بۆلۈڭ: كود مىقدارى كونترولدا، ئايرىم سىناققا بەرسە بولىدۇ، خاتالىقتا قايتۇرۇش ئەرزان. پۈتۈن چارەنى بىراقلا قىلىشنىڭ ئاقىۋىتى: diff چوڭ بولۇپ ھېچكىم تەكشۈرەلمەيدۇ، مەسىلە چىقسا قەيەرگە قايتىش نامەلۇم، دەسلەپكى پەرەز خاتا بولسا كېيىنكىسى بىكار.

ئالدى بىلەن Claude قا بۆلۈشنى تىزغۇزۇڭ، سىز جەزملەشتۈرگەندىن كېيىن بىرمۇبىر قىلىڭ:

ADR-023 نىڭ تاللانغان چارىسىنى ئايرىم ئېلان قىلىنىدىغان باسقۇچلارغا بۆل: تەلەپ:1. ھەر باسقۇچ ئايرىم سىناققا بېرىلىشى كېرەك (پۈتمىگەن باسقۇچقا تايانماسۇن)2. ھەر باسقۇچنىڭ ئېنىق قوبۇل قىلىش ئۆلچىمى بولسۇن3. ئىجرا رەت تەرتىپىنى بەلگىلە (ئالدىنلىقى يۇقىرىنى ئاۋۋال قىل)4. ھەر باسقۇچنىڭ خەتەر نۇقتىسىنى بەلگىلە ئالدى بىلەن بۆلۈش نەتىجىسىنى تىز، جەزملەشتۈرۈشىمنى كۈتۈپ ئاندىن بىرىنچى باسقۇچنى باشلا.

ئۇسۇل 2: TDD قىزىل → يېشىل → قايتا قۇرۇش

كونكرېت ۋەزىپە TDD غا ماس بولسا بۇ prompt نى ئىشلىتىڭ:

TDD بىلەن مۇلازىمەت ئۈزگۈچى لوگىكىسىنى ئىجرا قىل: بىرىنچى قەدەم (قىزىل): ئالدى بىلەن سىناق ياز، بۇ ئەھۋاللارنى قاپلا: - ئۇدا 3 مەغلۇبىيەتتە ئۈزۈش - ئۈزۈلگەن ۋاقىتتا بارلىق تەلەپلەرنى بىۋاسىتە رەت قىلىش - 60s دىن كېيىن يېرىم ئوچۇق ھالەتكە ئۆتۈش - يېرىم ئوچۇقتا 1 مۇۋەپپەقىيەت بىلەن ئەسلىگە كېلىش / مەغلۇبىيەتتە قايتا ئۈزۈش - پاراللېل ئىجرا بىخەتەرلىكى ئىككىنچى قەدەم (يېشىل): بارلىق سىناق ئۆتىدىغان ئەڭ ئاز كودنى ياز ئۈچىنچى قەدەم (قايتا قۇرۇش): كود قۇرۇلمىسىنى ياخشىلا، ھەممە سىناق يېشىل قالسۇن ھەر قەدەمدە ھەقىقىي سىناق ئىجرا قىلىپ نەتىجىنى كۆرسەت.

ئەمما TDD ھەممىگە شىپا ئەمەس— ئەھۋالغا قاراش كېرەك:

  • TDD غا ماس: يادرولۇق ساپ لوگىكا / ھالەت ماشىنىسى / ئالگورىزىم / bug تۈزىتىش / كۆرۈنمە يۈز كېلىشىمى
  • TDD غا ماس ئەمەس: ئىزدىنىشچان ئېچىش (تەلەپ ئېنىق ئەمەس) / ئالدى يۈز ئۆزئارا تەسىرى (ھەرىكەتنى unit test بىلەن تەسۋىرلەش تەس) / ئۈچىنچى تەرەپ بىرلەشتۈرۈشى (سىرتقى ھەرىكەتكە تايىنىدۇ) / بىر قېتىملىق script

ماس بولمىسا ئالدى بىلەن spike (تېز ئەندىزە) بىلەن يۈرگۈزۈپ، ئاندىن سىناق تولدۇرۇڭ؛ مەجبۇرلىماڭ.

ئۇسۇل 3: سىناق قوغدىغان قايتا قۇرۇش

بار كودنى ئۆزگەرتكەندە (يېڭى كود ئەمەس) ئېقىم قاتتىق:

adaptor_factory.go دىكى چوڭ switch-case نى (30+ case) قايتا قۇرماقچىمەن. بۇ قەدەملەر بويىچە ماڭ:1. ئالدى بىلەن بار سىناقلارنى ئىجرا قىلىپ ھەممىسى يېشىللىقىنى جەزملەشتۈر (baseline)2. switch ئەندىزىسىنى تەھلىل قىلىپ ئورتاق ھەرىكەتنى ئايرى3. ئىستراتېگىيە / تىزىملاش ئەندىزىسى بىلەن ئورۇن باسار لايىھە تۈز4. تەدرىجىي ئالماشتۇر؛ ھەر ئۆزگىرىشتىن كېيىن سىناق ئىجرا قىل5. ئاخىرىدا بارلىق سىناق يېشىل ۋە ھەرىكەت ئۆزگەرمىگەنلىكىنى جەزملەشتۈر چەك: سىرتقى API ھەرىكىتى ئۆزگەرمىسۇن. ھەر قەدەمدە سىناق يېشىل بولمىسا شۇ قەدەمنى دەرھال قايتۇر.

ئاچقۇچ «ھەر قەدەم ئۆزگەرگەندىن كېيىن سىناق» —ھەممىنى ئۆزگەرتىپ بولۇپ ئاندىن ئىجرا قىلىش ئەمەس. ھەممىنى بىراقلا قىلىپ قىزىل چىقسا، قايسى قەدەم خاتا بولغانلىقىنى بىلمەيسىز.

«ئۈچ قەدەم لايىھە + ئۈچ ئىجرا ئۇسۇلى» ۋاقىت ئالىدىغاندەك كۆرۈنىدۇ، ئەمما سېلىشتۇرساق لايىھەگە قوشۇمچە 1 سائەت كېيىنكى ئىجرا ۋە تەرەققىياتتا 10 ھەسسە تېجەيدۇ. چارىلەر سېلىشتۇرۇلغان، قارار ADR دا، باشقا تاللاشلار ساقلانغان، ئالماشتۇرۇش ئەرزان. بۇنى ئاتلاشنىڭ بەدىلى ھەر ئۆزگىرىشنىڭ دائىرىسى كونترولسىز بولۇپ، مەسىلىدە قايتا تەتقىق قىلىش.

ئىككىنچى يول: سىناقنى تاماملاش

ئالدى بىلەن Claude يازغان سىناقنىڭ ئورىكى

«XXX فۇنكسىيەگە unit test ياز» دېسىڭىز Claude 30 سېكۇنتتا بىر يۈرۈش بېرىدۇ. ئەمما ئەجەللىك مەسىلىسى:«ھەرىكەتنى دەلىللەش» ئۈچۈن ئەمەس، «كودنى قاپلاش» ئۈچۈن يازىدۇ。

تىپىك ساختا مۇسبەت:

func TestCalculateDiscount(t *testing.T) {    result := CalculateDiscount(100, 0.1) // assert يوق، پەقەت فۇنكسىيەنى چاقىرغان}

ياكى:

func TestParseConfig(t *testing.T) {    _, err := ParseConfig("valid.yaml")    assert.NoError(t, err) // پەقەت happy path، ھېچقانداق بىنورمال ئەھۋال سىنالمىغان}

بۇ سىناقنىڭ قاپلاش نىسبىتى يۇقىرى بولسىمۇ، ھەقىقىي bug نى تاپالمايدۇ. ئۆزۈم زىيان تارتقان: بىر قېتىم قاپلاش 90%+ ئىدى، ئەمما مۇھىم يولنىڭ چېگرا شارائىتى سىنالمىغان، تورغا چىققاندىن كېيىن بىۋاسىتە ئۆرۈلدى.

توغرا ئۇسۇل: دەلىللەش يېتەكچىلىكى + تاماملىقنى تەكشۈرۈش

قاتتىق قائىدە 1: دەلىللەش يېتەكچىلىكى（Anthropic رەسمىي ئەڭ ياخشى ئەمەلىيەتتە (code.claude.com/docs/en/best-practices)قايتا تەكىتلەنگەن بىر نۇقتا)

Claude قا دەلىللەش ۋاسىتىسى بېرىش يۇقىرى ئۈنۈملۈك ئۇسۇل —Claude ئۆزى دەلىللىيەلەيدىغاندا چىقىرىلما سۈپىتى زور ياخشىلىنىدۇ。

دەلىللەش بېرىشنىڭ تۆت ئۇسۇلى:

auth ئوتتۇرا قەۋىتىنى JWT غا قايتا قۇر. ئۆزگەرتكەندىن كېيىن بار سىناق يۈرۈشلۈكىنى ئىجرا قىل،بارلىق مەغلۇپ دېلولارنى تۈزىتىپ ئاندىن تۈگەت.

(سىناقنى دەلىل قىلىش)

كىرىش بېتىنىڭ ئورۇنلاشتۇرۇشىنى ئۆزگەرت. تۈگىگەندە ئېكران سۈرىتىنى كۆرسىتىپ UI چېكىنىشى يوقلۇقىنى جەزملەشتۈر.

(ئېكران سۈرىتىنى دەلىل قىلىش)

ئىشلەيدۇ دەپ پەرەز قىلماي، ھەقىقىي ئىجرا قىلىپ دەلىللە.

(«ئىجرا بولىدۇ دەپ قارايمەن»نى رەت قىلىش)

ئۆزگىرىشلەرنى ئەستايىدىل تەكشۈر، قالدۇرما يوقلۇقىنى جەزملەشتۈرۈپ ئاندىن commit قىل.

(ئۆزىنى تەكشۈرۈش)

ئاچقۇچ«should pass» بىلەن «probably OK»نى قوبۇل قىلماسلىق— سىناق يۈرۈپ، ئىسپات ئېلىنغاندىلا ھېساب.

قاتتىق قائىدە 2: ئۆزگىرىش تۈرى → سىناق دەرىجىسى خەرىتىسى

ئوخشىمىغان ئۆزگىرىشكە ئوخشىمىغان سىناق چوڭقۇرلۇقى:

ئۆزگىرىش تۈرىتاماملىنىشى شەرتقوشۇمچە تەۋسىيە
ساپ لوگىكا ئۆزگىرىشىunit + مودۇل + قايتىش سىنىقىچېگرا قىممىتى + بىنورمال يول
كۆرۈنمە يۈز ئۆزگىرىشى+ API سىنىقى + ماسلىشىش تەكشۈرۈشىخاتالىق كودى + ھوقۇق دەلىللەش
مودۇل ئارا ئۆزگىرىش+ بىرلەشتۈرۈش سىنىقى + سانلىق مەلۇمات بىردەكلىكىۋاقىتتىن ئېشىش ۋە قايتا سىناش
يادرولۇق زەنجىر ئۆزگىرىشى+ E2E + مەخسۇس سىناقتورغا چىقىرىش دەلىللەش تىزىملىكى
يۇقىرى خەتەرلىك ئۆزگىرىش+ ئۈنۈم ئاساس سىزىقى + قايتۇرۇش مەشىقىبىنورمال ئەھۋال مەشىقى

بۇ جەدۋەلنى تۈرنىڭ CLAUDE.md ھۆججىتىگە چاپلاڭ، Claude ھەر سىناق يازغاندا ئاپتوماتىك سېلىشتۇرىدۇ.

قاتتىق قائىدە 3: تاماملىقنى تەكشۈرۈش

«XXX تۈزىتىلدى» دېگەندىن كېيىن grep ئىجرا قىلىپ قالدۇق يوقلۇقىنى جەزملەشتۈرۈش شەرت.

# «ctx ئۈزۈلۈشى تۈزىتىلدى» دېگەندىن كېيىن بۇنى ئىجرا قىلىش شەرتgrep -c 'context.Background()' <بارلىق ئالاقىدار ھۆججەتلەر> # نەتىجە 0 ياكى ھەممىسى قانۇنلۇق ئىشلىتىش بولسۇن، قالدۇرما بولمىسۇن

«تۈگىدى دەپ قارايمەن» ئىسپات ئەمەس،grep -c نەتىجىسى ئىسپات.

تاماملىقنى تەكشۈرۈشنىڭ ماھىيىتى —AI نىڭ «تۈزىتىپ بولغاندەك» ھېسىنى ئىسپاتنىڭ ئورنىغا قويماسلىق. ھەر تۈرنىڭ قاپلاش نىسبىتى، قالغان case سانى باشقا؛ ئەمما «تامام دەۋاسى → grep بىلەن قالدۇق ئىزدەش → قالدۇرما تېپىلسا تولدۇرۇش» ئايلىنىشى بولۇشى شەرت.

يەنە بىر قەۋەت: Hooks بىلەن تەكشۈرۈشنى ئاپتوماتلاشتۇرۇش

ھەر قېتىم قولدا grep ئىجرا قىلىشنى ئەسلەشكە تايانسىڭىز، ئاخىرى قالدۇرما چىقىدۇ. Claude Code نىڭ Hooks مېخانىزمىبۇ تەكشۈرۈشلەرنى shell script قىلىپ، بەلگىلىك ھادىسىدە ئاپتوماتىك قوزغىتىدۇ؛ AI نىڭ سىز ئۈچۈن ئىشلىشىدە خاتالىقتىن ساقلىنىشنىڭ ئاچقۇچى شۇ.

ئەڭ ئەمەلىي ئىككىسى:

Pre-commit hook— Claude commit قىلىشتىن بۇرۇن توسۇپ، مەخپىي ھۆججەت ئاشكارىلىنىشىنى توسىدۇ:

# ~/.claude/hooks/pre-commit.shif git diff --cached --name-only | grep -E '\.(env|pem|key|secret)$'; then echo "❌ توسۇلدى: مەخپىي ھۆججەت بايقالدى"  exit 1fi

Post-edit hook— Claude ھۆججەت ئۆزگەرتكەندىن كېيىن ئاپتوماتىك lint / compile / test ئىجرا قىلىدۇ:

# ~/.claude/hooks/post-edit.shfor f in "$@"; do  case "$f" in    *.go) go vet "$f" || exit 1 ;;    *.ts) npx tsc --noEmit "$f" || exit 1 ;;    *.py) ruff check "$f" || exit 1 ;;  esacdone

«تەكشۈرۈشنى ئەسلەش»تىن «ئاپتوماتىك تەكشۈرۈش»كە ئۆتۈش —Claude Code نىڭ unattended ئىجرا بولۇشىنىڭ يادرولۇق نۇقتىسى. كۈندىلىك ئېچىش مۇھىتىمدا 6–7 hook بار؛ مەخپىي ھۆججەت، lint، compile ۋە مۇھىم سىناقلارنى قاپلايدۇ. Claude بۇلاردىن ئۆتەلمىسە ئۆزگىرىش ئامبارغا كىرەلمەيدۇ.

كېڭەيتىش: تولۇق DevTestOps ئېقىم Skill ى

يۇقىرىدىكى ئۈچ قائىدە «سىناقنى تاماملاش»نىڭ ئەڭ كۆپ ئىشلىتىلىدىغان قىسمىلا. تولۇق نۇسخىسىنى بىر Skill قىلىپ، نامىنى devtestopsدەپ قويدۇم؛ Claude Code نىڭ ~/.claude/skills/مۇندەرىجىسىگە ئورنىتىلسا پۈتۈن pipeline ئاپتوماتىك قوزغىلىدۇ.

Codex دوكلاتى چىققاندىن كېيىن شۇ Claude Code سۆھبىتىدە:

تۆۋەندىكىسى Codex پىكرى. بىرمۇبىر جاۋاب بەر:قوبۇل قىلىپ تۈزىتىش / تېخنىكىلىق ئىسپات بىلەن رەت قىلىش / مۇنازىرىگە قالدۇرۇش.كۆز بويامچىلىق بىلەن قوشۇلما؛ reviewer خاتا بولسا تېخنىكىلىق ئىسپات بىلەن سەۋەبىنى چۈشەندۈر. bug / لوگىكىلىق خاتالىق پىكرىنى تۈزەتكەندە ئالدى بىلەن سىناق يېزىپ قايتا كۆرسەت (قىزىل)،تۈزەتكەندىن كېيىن ئۆتكۈز (يېشىل). «تۈزەتتىم»نىڭ ئورنىغا «ئالدىدا مەغلۇپ / كېيىن ئۆتتى» ئىسپاتىنى بەر.قۇرۇلما تەۋسىيەسى / ناملاش / ئوقۇشچانلىق ئۈچۈن مەجبۇر سىناق يازما. [تەكشۈرۈش پىكرى كونتېكىستقا ئاپتوماتىك كىرىدۇ، كۆچۈرۈپ چاپلاش ھاجەتسىز]

بۇ قەدەم Claude ئويلىمىغان سىناق ئەھۋالىنى كۆپ تۇتىدۇ، بولۇپمۇ پاراللېل بەيگە ۋە خاتالىق يوللىرىنى.

D قەدەم: ئاخىرىدا لايىھە ھۆججىتى بويىچە ئىقتىدار تاماملىقىنى تەكشۈرۈش

كود ئىجرا بولۇشى ≠ ھەممە تەلەپنىڭ ئىجرا بولۇشى. بۇ پۈتۈن ھەمكارلىقنىڭ ئاخىرقى مۇداپىئەسى: «تېخنىكىلىق كود توغرا، مەھسۇلات تەلىپى پۈتمىگەن»نى توسىدۇ.

# Claude Code ئاساسلىق سۆھبىتىدەلايىھە ھۆججىتى ۋە git diff نى سېلىشتۇرۇپ بىرمۇبىر تەكشۈر: ## A. تەلەپ قاپلىشىھەر ئىقتىدار تەلىپىنى بەلگىلە:- ✅ ئىجرا قىلىنغان (كود ئورنىنى كۆرسەت)- ❌ ئىجرا قىلىنمىغان (قالدۇرما)- ⚠️ قىسمەن ئىجرا قىلىنغان (نېمە كەملىكىنى ئېيت) ## B. ئېقىم تاماملىقىھەر سودا ئېقىمىنىڭ تولۇق زەنجىرىنى ئىزلا:كىرىش → بىر تەرەپ قىلىش → ساقلاش → جاۋاب → ئالدى يۈز كۆرسىتىشى«كود بار، ئېقىم ئۈزۈك»نى تەكشۈر: سانلىق مەلۇمات يېزىلغان، ئوقۇغۇچى يوق / ھالەت ئۆزگەرگەن، خەۋەر يوق / API بار، ئالدى يۈز چاقىرمىغان. ## C. بىنورمال ئەھۋال قاپلىشىۋاقىتتىن ئېشىش / پاراللېللىق / تەكرار / قىسمەن مەغلۇبىيەتنىڭ ھەر بىرىگە ماس كود بولسۇن. ## D. ئىقتىدارسىز تەلەپلەرئۈنۈم يېتەمدۇ؟ بىخەتەرلىك چەكلىمىسى ئەمەلىيلەشتىمۇ؟ كۆزىتىش كۆرسەتكۈچى قوشۇلدىمۇ؟

ئاندىن Codex قا شۇ تەكشۈرۈشنى مۇستەقىل قىلدۇر.

ئىككى دوكلاتنى سېلىشتۇر:

  • ئىككىسىمۇ تاپسا → يۇقىرى ئالدىنلىق بىلەن تۈزىتىش
  • بىرىلا تاپسا → ھەقىقەتەن بار-يوقلۇقىنى دەلىللەش
  • خۇلاسە زىت بولسا → تالاش نۇقتىسىنى تىزىپ ئادەم قارار قىلىش

«يۇقىرى ئالدىنلىق تۈزىتىش»تە B قەدەمنىڭ ئېقىمىنى بىۋاسىتە قوللان: bug پىكرىدە ئالدى بىلەن قايتا كۆرسىتىدىغان سىناق (قىزىل)، تۈزەتكەندىن كېيىن دەلىللەش (يېشىل)؛ bug ئەمەسلىرىنى (تەلەپ قالدۇرما / ئېقىم ئۈزۈلۈشى / ئىقتىدارسىز كەمچىلىك) لايىھە ھۆججىتىنىڭ ئەسلى مەقسىتى بويىچە تولدۇر.«تاماملىق تەكشۈرۈشى»نى «تولدۇرۇپ قوياي» دېگەن سۆزگىلا چۈشۈرۈپ قويماڭ— بايقالغان ھەر ئىشنىڭ دەلىللىگىلى بولىدىغان ئىسپاتى بولۇشى شەرت.

ئىككى يادرولۇق بۇيرۇق:

/review-go: Go ئارقا تەرەپ چوڭقۇر تەكشۈرۈشى

ھازىرقى تارماقنىڭ main غا سېلىشتۇرغان بارلىق ئۆزگىرىشىنى چوڭقۇر تەكشۈر: 1. مېخانىكىلىق ئىزدەش (ئالدىنقى شەرت، ئاتلاشقا بولمايدۇ): - context.Background قالدۇقى - http.NewRequest قا ctx بېرىلمىگەن - io.ReadAll دا LimitReader يوق - ھەر چاقىرىشتا Transport/Client قۇرۇش 2. رېكۇرسىيەلىك تەكشۈرۈش: - يوپۇرماق تۈگۈنگىچە (HTTP / DB / ھۆججەت IO) - ھەر شاخنى قاپلاش (مۇۋەپپەقىيەت / مەغلۇبىيەت / تۆۋەنلىتىش / قايتا سىناش) 3. تاماملىقنى تەكشۈرۈش: - grep بىلەن تۈزىتىشتە قالدۇق يوقلۇقى - go build بىلەن كۆرۈنمە يۈز ماسلىشىشى 4. تارىخىي خاتالىق ساۋاقلىرىنى تەكشۈرۈش (قارشى ئەندىزە تىزىملىكىدىن)

/review-fullstack: تولۇق stack تەكشۈرۈشى

بۇنىڭدا /review-go ئاساسىغا ئالدى-ئارقا تەرەپ كېلىشىمى، ئىقتىدار تاماملىقى، ئامبار ئارا ئېكولوگىيە زەنجىرى تەسىرى قوشۇلىدۇ.

ئەڭ قىممەتلىك قىسمى: تارىخىي خاتالىق ساۋاقلىرى

پۈتۈن SOP نىڭ ئەڭ قىممەتلىك يېرى بۇيرۇق قېلىپلىرى ئەمەس.

ھەر خاتالىقتىن كېيىن توپلانغان«تارىخىي خاتالىق ساۋاقلىرى»— Pipeline نىڭ مەجبۇرىي تەكشۈرۈش تۈرىگە ئايلانغانلىرى.

AI تەكشۈرۈشى تاپالمىغان ھەر bug نى «قارشى ئەندىزە» قىلىپ Pipeline غا قوشىمەن.

ھەقىقىي بىر مىسال: بىر قېتىم ctx ئۈزۈلۈشىنى تۈزەتكەندە، Claude قا سىرتقى فۇنكسىيەنىڭ context.Background() نى ئۆتكۈزۈلۈپ كەلگەن ctxغا ئالماشتۇر دېدىم؛ ئۆزگەرتتى، سىناق ئىجرا قىلدى، تامام دېدى.

ئاندىن /codex:review بىلەن تەكشۈرسەم Codex قايتۇردى: سىرتقى ctx تۈزىتىلگەن، ئەمماشۇ ھۆججەتتىكى if err != nil نىڭ تۆۋەنلىتىش شېخى يەنىلا Backgroundچاقىرىۋاتىدۇ؛ شۇ مودۇلدىكى يەنە ئىككى helper مۇ جىمجىت context.Background() بىلەن يېڭى ctx قۇرۇۋاتىدۇ.

قايتا قارىسام ھەقىقەتەن شۇنداق. Claude نىڭ «تامام»ى پەقەت ئۆزگىرىش دائىرىسىدىكى بىر كىرىشنى قاپلىغان، پۈتۈن چاقىرىش زەنجىرىگە رېكۇرسىيە قىلمىغان.

تۈزىتىپ بولغاندىن كېيىن «پەقەت مۇۋەپپەقىيەت يولىنى ئىزلاپ، تۆۋەنلىتىش شېخىنى ئىزلىمەسلىك»نى ئايرىپ /review-go دىكى grep تەكشۈرۈش تۈرىگە قوشتىم. شۇنىڭدىن كېيىن ئوخشاش bug قايتا قاچمىدى.

«تارىخىي ساۋاق» مېخانىزمىنىڭ قىممىتى شۇ: بىر قېتىملىق كاشىلا قورقۇنچلۇق ئەمەس، ئوخشاش كاشىلىنىڭ تەكرارلىنىشى قورقۇنچلۇق. ھەر قېتىملىق خاتالىقنى Pipeline دا مەجبۇرىي تەكشۈرۈش قىلسىڭىز، كېلەر قېتىم Claude ياكى Codex ئاپتوماتىك تەكشۈرىدۇ.

بۇ 5 ئايدا ھەقىقىي قوشقانلىرىمدىن بىر نەچچىسى:

  1. پەقەت ئۆزگەرگەن فۇنكسىيەنى تەكشۈرۈپ، تارماق فۇنكسىيەگە رېكۇرسىيە قىلماسلىق — سىرتقى ctx تۈزىتىلگەن، چاقىرغان helper يەنىلا context.Background()
  2. پەقەت مۇۋەپپەقىيەت يولى، تۆۋەنلىتىش شېخى يوق — نورمال يولدىكى ctx تۈزىتىلگەن، ئەمما if err != nil دىن كېيىنكى تۆۋەنلىتىش يولىدا يەنىلا Background
  3. كۆرۈنمە يۈز ئىمزاسى ئۆزگەرگەن، بارلىق ئىجراچىلار تەكشۈرۈلمىگەن — dev دا main دا يوق ئىجرا ھۆججىتى بار، بىرلەشتۈرگەندىن كېيىن compile مەغلۇپ
  4. تۈزىتىلدى دېگەن، grep بىلەن قالدۇق دەلىللەنمىگەن — «ctx ئۈزۈلۈشى تۈزىتىلدى»، ئەمما شۇ ھۆججەتتىكى كۆپ helper دا Background بار
  5. قوشنا فۇنكسىيەدىكى ئوخشاش مەسىلە ئىزدەلمىگەن — بىر فۇنكسىيەنىڭ per-call Transport ى تۈزىتىلگەن، شۇ ھۆججەتتىكى باشقىلىرى ھەر چاقىرىشتا ياسايدۇ

تىزىملىك ئىشلەتكەنسېرى ئۇزىرايدۇ؛ ھەر بىر تۈر قوشۇلغاندا ئوخشاش bug نى ئۆتكۈزۈش نىسبىتى تۆۋەنلەيدۇ. بۇ Pipeline نىڭ توپلىنىدىغان پايدىسى: ھەر خاتالىق كېلەر قېتىملىق مەجبۇرىي تەكشۈرۈشكە ئايلىنىدۇ.

بىر ئاتالغۇ ئېنىقلىمىسى

Claude Code مۇھىتىدا كۆپ ئادەم «multi-agent» دېگەندە ئالدى بىلەن ئىچىگە قۇرۇلغان subagent مېخانىزمىنى ئويلايدۇ؛ بىر مودېلنىڭ كۆپ نۇسخىسى پاراللېل تەتقىق قىلىدۇ. كەڭ مەنىدە بولسا كۆپ مودېل، كۆپ قورال زەنجىرى، كۆپ context كۆزنىكى ئارىسىدىكى ھەمكارلىقمۇ كىرىدۇ. كۆپ نەقىل قىلىنىدىغان بىر سان Anthropic رەسمىي بىلوگىدىن《How we built our multi-agent research system》(anthropic.com/engineering/built-multi-agent-research-system): 2025-يىلى Opus 4 lead + Sonnet 4 subagent بىرلەشمىسى ئىچكى research باھالىشىدا يەككە Opus 4 تىن 90.2% يۇقىرى (دىققەت: بۇ research eval، كود تەكشۈرۈش eval ى ئەمەس، يۇمشاق دېتال ئېچىشقا بىۋاسىتە كېڭەيتكىلى بولمايدۇ).

بۇ ماقالىدىكى «كۆپ Agent ھەمكارلىقى» بولسا مودېل ئارا(Claude × Codex) تۈرى؛ ئاساسلىق مەقسەت يەككە مودېلنىڭ كۆرەلمەيدىغان نۇقتىلىرىنى ئازايتىش.

ئىككىسى توقۇنۇشمايدۇ؛ مۇھىم ئىقتىداردا ئىككىسىنىمۇ ئىشلىتىمەن:Claude subagent لىرى پاراللېل كود ئوقۇپ تەتقىق قىلىدۇ → Claude چارە ۋە ئىجرا چىقىرىدۇ → Codex ئۆزئارا تەكشۈرىدۇ. ئىچىگە قۇرۇلغان subagent نىڭ كونكرېت ئىشلىتىشىنى كېيىنكى ماقالىدە ئايرىم سۆزلەيمىز.

AI نېمە قىلالمايدۇ؟

ئۈچ يولدىن كېيىن چېگرانى قوشاي. بۇ مەزگىلدە ئېنىق بىلدىم: AI قانچە كۈچلۈك بولسىمۇ ئۈچ ئىشنى قىلالمايدۇ.

1. قۇرۇلما قارارى.

Claude چارە تىزالايدۇ، ئەمماقايسىسىنى تاللاشنى ئادەم بەلگىلىشى شەرت。

چۈنكى قۇرۇلما قارارى «سودىنىڭ كەلگۈسى يۆنىلىشى» ھەققىدىكى تۇيغۇنى تەلەپ قىلىدۇ؛ AI دا بۇ سانلىق مەلۇمات يوق.

2. سىستېما ئارا بىردەكلىكنى باھالاش.

بىر ئامبار ئىچىدە Claude ياخشى ئىشلەيدۇ.

ئەمما «بۇ 3 ئامبار ئارا كۆرۈنمە يۈز كېلىشىمى مۇۋاپىقمۇ»، «بۇ ئۆزگىرىش ئېكولوگىيەنىڭ باشقا ئامبىرىغا قانداق تەسىر قىلىدۇ» —

AI نىڭ context كۆزنىكى بۇلارنى سىغدۇرالمايدۇ.

ئومۇمىي خەرىتىنى ئادەم كاللىسىدا قۇرۇشى كېرەك.

3. مەھسۇلات تەجرىبە تۇيغۇسى.

«بۇ ئۆزئارا تەسىر ئىشلەتكۈچىگە ياقامدۇ»، «بۇ خاتالىق ئۇچۇرى قورقۇتامدۇ»، «ئىقتىدار سۈكۈتتە ئېچىلسۇنمۇ» —

AI دا ھەقىقىي ئىشلەتكۈچى ئىنكاسى يوق، پەقەت «ئادەتتىكى ئۇسۇل»نى بېرەلەيدۇ.

AI سىزدىكى باھالاش كۈچىنى چوڭايتىدۇ؛ باھالاش كۈچىنىڭ ئۆزى سىزدە بولۇشى كېرەك.

Opus 4.7 ھەققىدە: SOP ئۆزگىرىشى كېرەكمۇ؟

Claude Opus 4.7（anthropic.com/news/claude-opus-4-7） ئەمدىلا ئېلان قىلىندى؛ رەسمىي تەرەپ كود، ئۇزۇن ۋەزىپە ۋە يوليورۇققا ئەگىشىشتە ئالدىنقى نۇسخىدىن ياخشىلاندى دەيدۇ. ئەڭ كۆپ سورالغىنى: 4.7 دە بۇ SOP ئۆزگەرمەمدۇ؟

جاۋاب:ئاساسىي گەۋدىنى قايتا قۇرۇش ھاجەتسىز، ئەمما prompt، تەكشۈرۈش دەرۋازىسى ۋە سىناق harness ىنى قايتا قايتىش سىنىقىدىن ئۆتكۈزۈش كېرەك。

سەۋەب: مودېلنىڭ يېڭىلىنىشى «لايىھە قىلامدۇق، سىناق ئىجرا قىلامدۇق، ئۆزئارا تەكشۈرەمدۇق» دېگەننى ئىناۋەتسىز قىلمايدۇ. بۇ ئۈچى ئېقىم دەرىجىسىدىكى قارار، مودېل كۈچىگە باغلىق ئەمەس. ئەمما مودېل كۈچەيگەندە شۇ prompt ۋە كونا دەلىللەش دەرۋازىسى ماس كەلمەسلىكى مۇمكىن:

  • prompt ئىبارىسى: كونا نۇسخا كەڭچىلىك قىلغان مۈجمەل يوليورۇقنى 4.7 تېخىمۇ سۆزمۇسۆز ئىجرا قىلىشى مۇمكىن؛ دائىرە ۋە چىقىرىش شەكلى تېخىمۇ ئېنىق بولسۇن
  • تەكشۈرۈش دەرۋازىسى: ئىلگىرى /review-go قاتتىقلىقىنى 4.6 ھەرىكىتىگە قاراپ تەڭشىگەن بولسىڭىز، 4.7 غا ئالماشتۇرغاندا قايسى noise، قايسى ھەقىقىي مەسىلە ئىكەنلىكىنى قايتا ئۆلچەش كېرەك
  • سىناق harness نىڭ كۈتۈلگەن قىممىتى: «ئادەتتە مەغلۇپ، شۇڭا كەڭچىلىك» دېگەن case 4.7 دە مۇقىم ئۆتۈشى مۇمكىن؛ چىڭىتىشقا تېگىشلىكى چىڭىتىلسۇن

مەن ھازىر 4.7 بىلەن پۈتۈن SOP نى قايتا يۈرگۈزۈپ قايتىش دەلىللەش قىلىۋاتىمەن؛ Plan ھالىتىدىكى قۇرۇلما تەھلىلى، ئۇزۇن context تا پۈتۈن ئامبارنى بىراقلا ئوقۇش، ئۆزئارا تەكشۈرۈشنىڭ قارشىچانلىقىغا قارايۋاتىمەن. سان ۋە case ئېلىنغاندىن كېيىن كېيىنكى ماقالىدە يازىمەن.

(بۇ بۆلەك 2026-04 ھالىتىگە ئاساسەن يېزىلغان؛ كېيىنكى نۇسخىلار بىلەن كونكرېت ھۆكۈملەر يېڭىلىنىدۇ.)
