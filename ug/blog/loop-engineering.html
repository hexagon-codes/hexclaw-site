HexClaw AI نىڭ Loop Engineering ى: ئوچۇق كودلۇق Agent نىڭ كودىنى ئېچىپ، Prompt تىن Loop قىچە تۆت ئەندىزىنى قاتلاممۇقاتلام سېلىشتۇرۇش

Prompt → Context → Harness → Loop كونترول يۈزىنى ئۇچۇر قاتلىمىدىن سۆھبەت، سىستېما ۋە ۋاقىت قاتلىمىغا كېڭەيتىدۇ. ھەر بىر قاتلامدا بىر قاتلام قارار ھوقۇقىنى بېرىسىز. قايسىسى تولۇق، قايسىسى تولۇقلىنىۋاتىدۇ ۋە «تامام» نېمە دېگەنلەر ھەقىقىي كود بىلەن كۆرسىتىلىدۇ.

AI ساھەسىدىكى ئاچقۇچلۇق سۆزلەر بۇ يىللاردا توختىماي سىرتقا كېڭەيدى: ئاۋۋال Prompt Engineering، ئاندىن Context Engineering، Harness Engineering، يېڭى Loop Engineering بولسا يېقىندالا چىقتى. مودا سۆز ئۇلاش مۇسابىقىسىدەك ئاڭلىنىدۇ، ئەمما بىللە قارىغاندا ئوخشاش بىر سىزىقنىڭ يىراققا كېڭىيىشى. ھەر بىر سۆز بىلەن بىر تەسىرلىك گەپمۇ كېلىدۇ. Claude Code نى ياراتقان Anthropic تىكى Boris Cherny سەھنىدە مۇنداق دېدى:

«مەن ئەمدى Claude غا prompt يازمايمەن. مەن ئىشلىتىۋاتقان loop لار بار؛ ئۇلار Claude غا prompt بېرىپ، كېيىن نېمە قىلىشنى ئۆزى ئويلايدۇ. مېنىڭ ئىشىم loop يېزىش.»
يەنى Claude غا بىۋاسىتە بۇيرۇق بېرىشنىڭ ئورنىغا، ئۇنىڭغا بۇيرۇق بېرىدىغان ئايلانمىلارنى لايىھەلەش.

شۇ ۋاقىتتا دېگۈدەك، OpenClaw نى قۇرغۇچى Peter Steinberger ناھايىتى كۆپ تارقالغان تېخىمۇ قىسقا بىر يازما چىقاردى:

«ئەمدى coding agent لارغا prompt يېزىش بىلەنلا بولماڭ. Agent لىرىڭىزغا prompt بېرىدىغان loop لارنى لايىھەلەڭ.»
يەنى كودلاش Agent ىغا بىۋاسىتە بۇيرۇق بېرىشتىن، ئۇنىڭغا بۇيرۇق بېرىدىغان ھالقىنى قۇرۇشقا ئۆتۈش.

Google Cloud AI دىرېكتورى Addy Osmani بۇ ھادىسىگە Loop Engineering دەپ نام بەردى. ئۈچ كىشىنىڭ گېپىنىڭ ئارىسىدا بىر نەچچە كۈنلا پەرق بار؛ بۇ ئاتالغۇ تېخى يېڭى.

ئەمما ئەڭ ساپ شەكلىنى 2025-يىلىلا بىرسى يازغان: Geoffrey Huntley نىڭ Ralph ھالقىسى، يادروسى بىر قۇر bash:

1while :; do cat PROMPT.md | claude-code ; done

ھەر ئايلانمىدا يېڭى context كۆزنىكى ئېچىلىدۇ؛ ھالەت سۆھبەت تارىخىغا ئەمەس، ھۆججەت سىستېمىسى ۋە git قا تايىنىپ يەتكۈزۈلىدۇ. مەھەللە بۇنى بىر جۈملىگە يىغدى: Agent ئۇنتۇيدۇ، ئامبار ئۇنتۇمايدۇ. بۇ پەقەت شوئار ئەمەس: HexClaw ئەسلەتمە، ماھارەت ۋە ھالەتنى ئۆز كومپيۇتېرىڭىزدا git diff قىلىدىغان ئاددىي تېكىستكە يېزىدۇ؛ بۇ پۈتۈن لايىھەنىڭ ئاساسىي رەڭگى، كېيىنكى ھەر قاتلامدا يەنە ئۇچرايدۇ.

بۇ گەپ چىققاندىنلا سوئالمۇ كەلدى، تەنقىدنىڭ ئاساسى بار: بۇ ئون نەچچە يىل بۇرۇنقى CI/CD نى قايتا كەشىپ قىلىش ئەمەسمۇ؟ قوزغىتىش cron/webhook، ئايرىش «Worktree sandbox»، ئوچۇق ئېيتقاندا Docker قاچىسى، تەكشۈرۈش ESLint/Jest؛ يېشىل بولسا ئۇقتۇرۇش، قىزىل بولسا قايتا يازدۇرۇش. بۇ ئېقىم Jenkins دەۋرىدىلا بار ئىدى، پەقەت AI قەنتى بىلەن ئورالغان. بۇ گەپ توغرا. تېخىمۇ ئىچكى يادروسى تېخىمۇ كونا كونترول نەزەرىيەسىدىكى قايتما ھالقا: كۆزىتىش، سېلىشتۇرۇش، ھەرىكەت، تەكرارلاش. ئۇ تېرموستات، PID كونتروللىغۇچ ۋە Kubernetes نىڭ Reconciliation Loop ى بىلەن ئوخشاش نەسەب دەرىخىدىكى شاخلار. بۇمۇ توغرا.

شۇڭا «كونا شارابنى يېڭى بوتۇلكىغا سالدىمۇ؟» دەپ تالاشقاندىن نەتىجە چىقمايدۇ، بۇمۇ مۇھىم ئەمەس. قىممەتلىك سوئال باشقا: ھەقىقىي بىر سىستېما بۇ ھالقىنى راست تاقىدىمۇ، ياكى ھەممەيلەن ئېغىزىدىلا يېپىق ھالقا دەمدۇ؟ ئۇقۇمنى ھەممە ئادەم سىزالايدۇ، PPT دا ئوقنى باش-ئاخىر تۇتاشتۇرۇش ئاسان. قىيىنى كودقا چۈشۈرۈش: مۇستەقىل ھۆكۈمچى كىم، loop نېمىگە ئاساسەن توختايدۇ، «تامام»نى كىم، قايسى ئۆلچەم بىلەن بەلگىلەيدۇ؟

بۇ ماقالە نەزەرىيەنى تەكرارلىمايدۇ، ئۇقۇم ۋە ئوخشىتىش ھەققىدە ياخشى ماقالە يېتەرلىك. ئۇ باشقا ئىش قىلىدۇ: HexClaw ئوچۇق كودلۇق Agent نىڭ كودىنى ئېچىپ، Prompt تىن Loop قىچە تۆت قاتلامنى بىرمۇبىر سېلىشتۇرىدۇ. ھەر قاتلام ھەقىقىي ھۆججەت، تۇراقلىق قىممەت ۋە توختاش شەرتىگە چۈشىدۇ. ئوقۇپ بولغاندا يېڭى مودا سۆزلەر ئەمەس، ئىشلەپچىقىرىش دەرىجىلىك loop نىڭ قايسى زاپچاسلاردىن قۇراشتۇرۇلغانلىقى ۋە نېمىشقا شۇ قىممەتنى ئالغانلىقىنى كۆرىسىز. تولۇق بولغان قاتلام تولۇق چۈشەندۈرۈلىدۇ، يېرىم بولغان يەردە «بۇنى تېخى تولۇقلاۋاتىمەن» دەپ ئېنىق بەلگىلىنىدۇ. بولۇپمۇ Loop قاتلىمىدا ئۆزۈمنىمۇ ھەيران قالدۇرغان ھەقىقىي يېپىق ھالقا ۋە پۈتۈن ساھە تېخى ئاتلاپ ئۆتەلمىگەن توسۇق بار.

ماقالىنىڭ ئاساسىي ھۆكۈمى
بۇ تۆت ئەندىزە بىر-بىرىنى ئالماشتۇرمايدۇ، قاتلاممۇقاتلام ئۈستىلىنىدۇ. ئۇلارنى باغلىغان يوشۇرۇن سىزىق شۇكى، ھەر بىر قاتلام سىرتقا كېڭەيگەندە بىر قاتلام قارار ھوقۇقىنى بېرىسىز: ئىپادە → ئۇچۇر تاللاش → جەرياننى كونترول قىلىش → باشلاش ۋە قوبۇل قىلىش ھوقۇقى.
HexClaw دا تۆت قاتلامنىڭ ھەممىسىدە ھەقىقىي كود بار. ئەمما ھەقىقىي يۇقىرى چەك ئالدىنقى ئۈچىدە ئەمەس، تۆتىنچىدىكى ئەڭ قىيىن ئىككى ئىشتا: «نىشان»نى قانداق فورماللاشتۇرۇش، «تامام»نى قانداق مىقدارلاشتۇرۇش. بۇ ئىككىسىنى HexClaw مۇ پۈتۈن ساھەگە ئوخشاش تېخى تولۇقلاۋاتىدۇ.

تۆۋەندىكى رەسىم HexClaw كودىدىكى «كونترول يۈزىنى سىرتقا كېڭەيتىش»: تۆت قاتلامدا ھەقىقىي زاپچاس ۋە تۇراقلىق سان، Loop قاتلىمىدا ھەقىقىي يېقىنلىشىش ھالقىسى ۋە تېخى ئۆتۈلمىگەن توسۇق كۆرسىتىلگەن.

بىرىنچى قاتلام، Prompt: ئۇچۇر قاتلىمىدا «ئىپادە»نى بېرىسىز

دەسلەپ ھەممەيلەن Prompt AI دەۋرىدىكى ئەڭ مۇھىم ماھارەت دەپ ئىشەندى. System prompt قانداق يېزىلىدۇ، few-shot قانداق تىزىلىدۇ، پىكىر زەنجىرى قانداق يېتەكلىنىدۇ؛ بىر بۇيرۇق ئەڭ ياخشى ھالەتكە كەلتۈرۈلىدۇ. كومپيۇتېر تىلىدا بۇ بىر جۈملىنى ياخشى يېزىش، بىر قۇر print نىڭ ئىپادىسىنى ئويلاشقا ئوخشايدۇ. بېرىدىغىنىڭىز «بۇ گەپ قانداق ئېيتىلسۇن» دېگەن ھوقۇق.

HexClaw دا بۇ قاتلامغا لازىم نەرسىلەر بار: تەھرىرلىنىدىغان ياردەمچى خاراكتېرى SOUL، system prompt باشقۇرۇش ۋە ساقلاپ قايتا ئىشلىتىدىغان Prompt كۈتۈپخانىسى. ئەمما بۇنى كۆپ سۆزلىمەيمەن، چۈنكى ئۇ تېزلا تامغا سوقۇلدى: مودېل كۈچەيگەنسېرى Prompt نىڭ قوشۇمچە پايدىسى تۆۋەنلەيدۇ. تېخىمۇ مۇھىمى، بىر ئايلانما بۇيرۇق كۆپ قەدەملىك، سۆھبەتلەر ئارا، قايتا-قايتا تۈزىتىش بىلەن پۈتىدىغان ئىشنى كۆتۈرەلمەيدۇ. بىر جۈملىنى قانچە چىرايلىق ئېيتسىڭىزمۇ مودېل پەقەت «ياخشى جاۋاب بېرىدۇ»، «ئىشنى پۈتتۈرمەيدۇ». شۇڭا بىر قاتلام سىرتقا، بۇ جۈملىدىن مودېل ئەتراپىدىكى مۇھىتقا قاراش كېرەك.

ئىككىنچى قاتلام، Context: سۆھبەت قاتلىمىدا «ئۇچۇر تاللاش ھوقۇقى»نى بېرىسىز

ئىككىنچى ئەۋلادنىڭ تونۇش يېڭىلىنىشى مۇھىم: مەسىلە «مودېلنى قانداق قايىل قىلىش»تىن «مودېل تۇرغان مۇھىتنى قانداق قۇرۇش»قا ئۆتتى. Context كۆزنىكى كەمچىل بايلىق؛ نېمىنى سېلىش، نېمىنى سالماسلىق ۋە قايسى تەرتىپتە سېلىش مودېلنىڭ ھۆكۈم يولىنى بەلگىلەيدۇ. كومپيۇتېر تىلىدا بۇ ئىچكى ساقلىغۇچ باشقۇرۇش ۋە قولدا GC: كۆزنەك RAM، كىمنى چىقىرىش ۋە كىمنى قىسقارتىشنى ئۆزىڭىز بەلگىلەيسىز. بېرىدىغىنىڭىز «قايسى ئۇچۇرنى كۆرۈش»نى تاللاش؛ ئۇچۇر دائىرىسىنى سىز بەلگىلەپ، مودېل ئىچىدە ئۆزى ئىشلەيدۇ.

HexClaw بۇ قاتلامدا ئاساسلىق، كۆپىنچىسىنىڭ ھەقىقىي تۇراقلىق قىممىتىنى تەكشۈرگىلى بولىدۇ:

  • ئۈچ ئۆلچەملىك ئەسلەش: ئەسلەتمە ئاددىي تەتۈر ۋاقىت رېتى ئەمەس؛ recency، يېقىنلىق × importance، مۇھىملىق، ئەسلەش ماسلىق قېتىم سانى بىلەن ئۆزىنى تۈزىتىدۇ، كۆپ ئەسلەنگەنسېرى مۇھىم، LLM مۇقىم نومۇر بەرمەيدۇ × relevance، مۇناسىۋەت، hybrid 0.7 ۋېكتور ۋە 0.3 BM25. ۋېكتورلاشتۇرغۇچ بولمىسا ساپ BM25 غا يۇمشاق تۆۋەنلەيدۇ.
  • پىكىر ئۆزگەرسە قاپلىماي كۈچتىن قالدى دەپ بەلگىلەيدۇ: ئايرىپ تەكرار چىقىرىش ئوخشاشلىق بوسۇغىسى 0.65. زىتلىق بولسا supersede ئارقىلىق تارىخ ساقلايدۇ؛ ValidFrom / ValidTo خاتىرىلىنىپ، پەقەت ھازىرقى كۈچكە ئىگە تۈر ئەسلىتىلىدۇ. كونا نەشر ئۆچۈرۈلمەي قايتا كۆرۈشكە قالىدۇ.
  • قۇرۇلمىلىق قىسقارتىش، ئاددىي خاتىرە خۇلاسىسى ئەمەس: تارىخ ئۇزارسا ئاددىي كېسىش ياكى تەبىئىي تىلدا قايتا ئېيتىش ئەمەس، «نېمە قىلىندى، نېمە قارار قىلىندى، نېمە قالدى» دەپ قۇرۇلمىلىق خۇلاسىلىنىپ ئەسلى تارىخنى ئالماشتۇرىدۇ. بۇ ساھەدىكى ئاساسلىق ئۇسۇلغا ماس. ئۇزۇن log ياكى سىرتقى ھۆججەت ئوقۇغاندا بالا Agent ئايرىپ ئوقۇپ، پەقەت خۇلاسىنى ئاساسىي كۆزنەككە قايتۇرىدۇ، مەينەت سانلىق مەلۇمات ئاساسىي لىنىيەنى بۇلغىمايدۇ.
  • قورال context چېگراسى: Agent غا grep / browser سەپلەنسە، توغرا context نى ئۆزى ئېلىپ كېلەلەيدۇ. قورالنى كونترول قىلىش ئۇنىڭ يېتەلەيدىغان ئۇچۇر چېگراسىنى ۋاسىتىلىك كونترول قىلىش.

ئەسلەتمىنىڭ ئۈچ قاتلام قۇرۇلمىسى، ئۈچ ئۆلچەملىك ئەسلەش، يېرىم ئۆمرى ۋە كېچىدە «چۈش كۆرۈپ» ئارخىپ رەتلىشىنى ئالدىنقى ماقالىدە مەخسۇس ئاچقانىدىم. بۇ يەردە پەقەت تىلغا ئالىمىز: چۈش كۆرىدىغان Agent ئەسلەتمىسى.

ئەمما بۇ قاتلام ياخشى بولغاندىمۇ يېڭى مەسىلە چىقتى، ئۈچىنچى ئەۋلادنى قوزغىغىنىمۇ شۇ: context تولۇق بولسىمۇ، Agent ئۇزۇن ۋەزىپىدە يەنىلا يىقىلىدۇ. ھەقىقىي ۋەزىپە «بىر قېتىم پىكىر يۈرگۈزۈش» ئەمەس، «قايتما ئۇچۇرلۇق ھەرىكەتلەر زەنجىرى». مودېل كۆپ قەدەم ئىشلەشكە باشلىسا كەمچىلىكى يوشۇرۇنمايدۇ: «تەكرارلىغۇچ»قا ئايلىنىپ ئوخشاش ئۇسۇلنى قايتا ئىشلىتىپ token كۆيدۈرىدۇ، ھوقۇقتىن ھالقىپ خەتەرلىك ئىش قىلىدۇ ياكى يېرىم يولدا چۆكىدۇ. پەقەت ئۇچۇر يېتەرلىك ئەمەس، قائىدە ۋە توساق كېرەك.

ئۈچىنچى قاتلام، Harness: سىستېما قاتلىمىدا «جەرياننى كونترول قىلىش ھوقۇقى»نى بېرىسىز

Harness نىڭ ئەڭ ماس چۈشەندۈرۈلۈشى Mitchell Hashimoto نىڭ Agent = Model + Harness دېگەن سۆزى. مودېل ماتور، Harness ئۇنى قاپلىغان پۈتۈن runtime: قورال ئېقىمى، I/O ۋە بىخەتەرلىك قېپى. كومپيۇتېر تىلىدا ئۇ Agent نىڭ ئىزاھلىغۇچىسى ياكى مەۋھۇم ماشىنىسى. Thoughtworks تىكى Martin Fowler بىلەن Birgitta Böckeler كونترول نەزەرىيەسى بىلەن ئىككىگە ئايرىغان: Guides، ئالدىنقى كونترول Agent ئىش قىلىشتىن بۇرۇن ئۆلچەم، Skill ۋە قاتتىق چەك بىلەن نېمە قىلماسلىقنى ئېيتىدۇ؛ Sensors، قايتما كونترول ئىش قىلغاندىن كېيىن سىناق نەتىجىسى، تۈر تەكشۈرۈش ۋە ھۆكۈمچى بىلەن كۆزىتىپ، پەرقنى كېيىنكى ئايلانمىغا قايتۇرىدۇ. بۇ قاتلامدا بىر قېتىملىق ئىجرا ئىچىدىكى جەرياننى كونترول قىلىش بېرىلىدۇ: قايسى قورال، قايسى يول، قاچان تارىخ قىسقارتىشنى ئۆزى بەلگىلەيدۇ؛ ۋەزىپە قەيەردىن باشلىنىدۇ ۋە بىخەتەرلىك چېگراسى قەيەردە، يەنىلا سىزنىڭ قولىڭىزدا.

«ئىشتىن بۇرۇن يېتەكلەش، ئىشتىن كېيىن تۈزىتىش» قۇرۇلمىسى بىكاردىن چىقمىغان، ئاكادېمىيەدە ئېنىق نەسەبى بار. Agent نىڭ «ئويلاش → قورال چاقىرىش → نەتىجە كۆرۈش → قايتا ئويلاش» نۆۋەتلىشىشىنى ReAct، Yao قاتارلىقلار، ICLR 2023، Thought–Action–Observation ئۈچ قەدەمگە فورماللاشتۇرغان. HexClaw نىڭ «قورال تىزىملىكىنى مودېلغا ھەمىشە بېرىش، ئۇ چاقىرماقچى بولسا ئىجرا قىلىپ داۋاملاشتۇرۇش» ھالقىسى ماھىيەتتە ReAct نىڭ ئىنژېنېرلىق يولغا قويۇلۇشى. Harness مودېلنى ئەقىللىق قىلمايدۇ، ئۇنىڭ ئىزدەيدىغان بوشلۇقىنى كىچىكلىتىدۇ. T قەدەملىك ۋەزىپىنىڭ ھەر قەدىمىدە N نامزات ھەرىكەت بولسا، ئاددىي يول سانى NT بويىچە پارتلايدۇ. ئالدىنقى چەك قويۇلسا، ئون تۈر ھەرىكەت چەكلىنىپ، بەش قەدەم مەجبۇرىي بولسا، ھەر قەدەمنىڭ ئۈنۈملۈك شاخ ئامىلى N دىن كىچىك قىممەتكە چۈشىدۇ، ئېكسپونېنتنىڭ ئاساسىمۇ تۆۋەنلەيدۇ. ئۇچۇر نەزەرىيەسىدە H(action│rules) ≪ H(action)، قائىدە بېرىلگەندە كېيىنكى قەدەمنىڭ ئېنىقسىزلىقى ئازىيىدۇ. بۇ قۇرۇق سۆز ئەمەس: LangChain ئېنىق سېلىشتۇرما قىلغان؛ ئاستىدىكى gpt-5.2-codex مودېلىنى ئۆزگەرتمەي، پەقەت Harness نى ئىنچىكىلەتكەندە Agent نى ھەقىقىي تېرمىنال ۋەزىپىسىدە باھالايدىغان TerminalBench 2.0 ئۆتۈش نىسبىتى 52.8% تىن 66.5% كە، رەت Top 30 دىن Top 5 كە چىققان. ئوخشاش مودېل قېپى ئالماشقاندا كۈچەيدى؛ چۈشەندۈرۈشى سىرلىق ئەمەس، ئەقىل ئۆسمىدى، سىز ئۇنىڭ سىناش-خاتالىشىش ئېنتروپىيەسىنى ئالدىن ئازايتتىڭىز.

HexClaw نىڭ بۇ قاتلىمىدىن ھەقىقىي تۇراقلىق سانى بار بىر نەچچىنى تاللايمەن:

  • قورال ھالقىسى ۋە قاتتىق ئايلانما چېكى: Harness نىڭ يۈرىكى. قورال تىزىملىكى مودېلغا ھەمىشە بېرىلىدۇ، چاقىرىش بولسا ئىجرا قىلىپ، ئاخىرقى جاۋابقىچە ئايلىنىدۇ. ئادەتتىكى ھالەتتە ئەڭ كۆپ 25 ئايلانما، خامچوت كونترول ئېچىلغاندا مۇتلەق بىخەتەر يۇقىرى چەك 50. بۇ قۇرۇق تەكرارنىڭ ئاخىرقى دەرۋازىسى. چەككە يېتىش خاتالىق ئەمەس؛ مودېل چىقارغان قىسمەن نەتىجە بىلەن «ئايلانما چېكىگە يەتتى، داۋاملاشتۇر دېسىڭىز داۋاملىشىمەن» قايتىدۇ، يۇمشاق تۆۋەنلەيدۇ.
  • قورال قايتا سىنىشى پەقەت ۋاقىتلىق خاتالىقتا ئارقىغا چېكىنىدۇ: سۈكۈتتىكى ۋاقىت چەكلىمىسى 30s، browser ئۈچۈن 120s، code_exec ئۈچۈن 60s. قايتا سىناش 1s دىن باشلاپ ×2، ئەڭ كۆپ 8s لىك ئېكسپونېنتسىيال چېكىنىش؛ ئەمما پەقەت ئېنىق ۋاقىتلىق خاتالىق، چاستوتا چەكلىمىسى ياكى يۇقىرى ئېقىم داۋالغۇشىدا. ئىناۋەتسىز key ياكى مودېل يوق دېگەندەك قايتا سىنىغاندىمۇ پايدىسىز خاتالىقتا قارىغۇلارچە ۋاقىت ئىسراپ قىلمايدۇ.
  • ھوقۇق قاتتىق دەرۋازىسى، ئالدىنقى كونترول ۋە قاتتىق چەك: خەتەرلىك ھەرىكەتنى prompt دىكى يۇمشاق چەكتىن كود قاتلىمىدىكى قاتتىق چەككە كۆتۈرىدۇ. بىرلىككە كەلگەن ھوقۇق دەرۋازىسى سۈكۈتتىكى ھالەتتە ئوچۇق، ئاقىۋەتلىك ھەرىكەت «تەستىق كېرەك»كە ئۇچرايدۇ. cron/webhook قاتارلىق ئۆزئارا تەسىرسىز ئاپتوماتىك سۆھبەتتە ئۆزىنى ئۆستۈرۈش ۋە ئۆزىنى ۋاقىتلاشتۇرۇش قوراللىرىمۇ چىقىرىلىدۇ، loop ئۆزىگە ھوقۇق قوشۇپ كونترولدىن چىقىشى توسۇلىدۇ.
  • قۇرۇلمىلىق sandbox: cron لىنىيەسى بىر جۈملىنى Starlark سكرىپتىغا تۈزۈپ، سۈكۈتتىكى نۆل ھوقۇق، پەقەت ئوچۇق كىرگۈزۈلگەن ئىقتىدارلىق sandbox تا ئىجرا قىلىدۇ؛ 8MiB ئىچكى ساقلىغۇچ، 100 مىليون قەدەم، 300s ۋاقىت چېكى. بۇ ئىقتىدار بىخەتەرلىك مودېلىنى «تور ئىش كۈچى» ماقالىسىدە تەپسىلىي ئاچقان.

بۇ قاتلامنىڭ توغرا بولۇش ئۆلچىمى: ھېچكىم قاراپ تۇرمىغاندا Agent ئون نەچچە قەدەملىك، كۆپ قوراللىق ئۇزۇن ۋەزىپىنى context پارتلاتماي، ئۆلۈك ھالقىغا كىرمەي، قايتۇرغىلى بولمايدىغان خەتەرلىك ئىش قىلماي پۈتتۈرەلسۇن؛ چۆكسىمۇ ئەڭ يېقىن تەكشۈرۈش نۇقتىسىدىن داۋاملىشالىسۇن.

ئەمما Harness نىڭ يىلتىز چېگراسى بار: ئۇ بىر چەكلىك ۋەزىپىگە مۇلازىمەت قىلىدۇ. ئاشخانا دەپ تەسەۋۋۇر قىلايلى؛ ئاشپەزگە رېتسېپ ۋە قولايلىق قورال بېرىسىز، بىر تاماق چىقسا ھالقا تۈگەپ، پۈتۈن ئېقىم چېكىنىدۇ. ئەمما بەزى ئىش «تاماق چىقتى، ئىش تۈگىدى» ئەمەس: جامائەت پىكرىنى ھەر كۈنى كۆزىتىش، بىلىم ئامبىرىنى ئۇزاق مۇددەت تولدۇرۇش، Bug تىزىملىكىنى داۋاملىق تازىلاش. بۇ ئاخىرقى نۇقتىسى يوق، پەقەت كېيىنكى ئايلانما قاچان باشلىنىدۇ دېگەن ئۈزلۈكسىز ۋەزىپىنى ئاشخانا مودېلى كۆتۈرەلمەيدۇ. ئۇنىڭغا بىر ئاشخانا ئەمەس، رېستوران كېرەك: قاچان ئېچىلىدۇ، جەريان قانداق تىزىلىدۇ، ناچار باھا قايسى ئېقىمغا كىرىدۇ؛ ھەممىسى لايىھەلىنىپ ئاندىن ئۇزاق مۇددەت ئۆزى ئايلىنىشى كېرەك. تۆتىنچى قاتلام شۇنىڭدىن چىقتى.

تۆتىنچى قاتلام، Loop: ۋاقىت قاتلىمىدا باشلاش ۋە قوبۇل قىلىش ھوقۇقىنى بېرىش؛ يېرىمى تولۇق، يېرىمى تېخى تولۇقلىنىۋاتىدۇ

بۇ قاتلامدا خاراكتېر ئۆزگىرىدۇ. ئالدىنقى ئۈچتە باشلاش كۇنۇپكىسى سىزنىڭ قولىڭىزدا: ۋەزىپە دەيسىز، Agent ئىجرا قىلىپ، كېيىنكى گېپىڭىزنى كۈتىدۇ. Loop Engineering نىڭ يادرولۇق مەسىلىسى: Agent نى ئۆزىڭىز قوزغاتماي، قاچان قوزغىتىش، قانچىنى قوزغىتىش، نەتىجىنى كىم قوبۇل قىلىش ۋە كېيىنكى ئايلانمىنى قەيەردىن داۋاملاشتۇرۇشنى بەلگىلەيدىغان سىستېما قۇرۇش. كومپيۇتېر تىلىدا بۇ كونترول ئېقىمى، بىر قېتىم چاقىرىشنى تەكرارلاش، قايتا سىناش ۋە يېقىنلىشىشقا ئايلاندۇرۇش. بېرىدىغىنىڭىز ۋەزىپىنىڭ باشلاش ۋە قوبۇل قىلىش ھوقۇقى.

بۇ قاتلامنى ماختاشمۇ، ئاجىزلىقىنى ئاشكارىلاشمۇ ئەڭ ئاسان. HexClaw دا ئۇنى تۆتكە ئايرىپ، قىلىنغان ۋە قىلىنمىغانلىرىنى تەڭ كۆرسىتىمەن.

① ئاۋۋال ئېنىقلايلى: cron «يۈرەك سوقۇشى»، Loop ئەمەس

Loop ئايلىنىش ئۈچۈن بىرىنچى زاپچاس «يۈرەك سوقۇشى»: timer، cron ياكى webhook، ئادەم كۇنۇپكا باسمايمۇ قوزغىتىدىغان مەنبە. HexClaw cron ىدا ئۆزلۈكىدىن تۈزىتىشمۇ بار: بىر سكرىپت ۋەزىپە ئارقا-ئارقىدىن 3 قېتىم مەغلۇپ بولسا، مەغلۇبىيەت context ى بىلەن ئۆزلۈكىدىن بىر قېتىم قايتا تۈزۈلىدۇ؛ 24h كۆزنىكىدە ئەڭ كۆپ 2 قېتىم، مەڭگۈ بۇزۇق يۇقىرى ئېقىم token نى كۆيدۈرمىسۇن.

ئەمما cron ماقالىسىدە ئېنىق ئېيتقان گەپنى بۇ يەردىمۇ ساقلاش كېرەك: cron نىڭ ئۆزى ئوچۇق ھالقا، Loop ئەمەس. ئۇ «ۋاقىتتا مۇقىم سكرىپت ئىجرا قىلىش». مەغلۇبىيەتنى ئۆزى تۈزىتىش قايتما زاپچاس، ئەمما «نىشانغا سېلىشتۇرۇپ، تاماممۇ دەپ باھالاپ، بولمىسا خۇلاسە بىلەن يەنە بىر ئايلانما» قىلىدىغان يېقىنلىشىش يېپىق ھالقىسى يوق. يۈرەك سوقۇشى لازىم زاپچاس، بىراق يۈرەك سوقۇشى بار دېگەن Loop دېگەن ئەمەس. ھەقىقىي يېپىق ھالقا باشقا يەردە.

② ھەقىقىي يېقىنلىشىش ھالقىسى: orchestrate ۋە مۇستەقىل نازارەتچى

كۆپ كىشىنىڭ كاللىسىدىكى Loop Goal → Agent → Done. ئەمما ھەقىقىي يېپىق ھالقا مۇنداق:

Goal → Agent → Evaluate → Score → Feedback → Agent → Evaluate → Score → …

بۇ ئاددىي loop ئەمەس، ئەلالاشتۇرۇش سىستېمىسى؛ قۇرۇلمىسى كۈچەيتىپ ئۆگىنىشكە ئوخشاشلىشىدۇ، ئەمما پەقەت شەكلى ئوخشاش: باھالاش ۋە قايتما ئۇچۇر بار، مۇكاپات سىگنالى ياكى ئىستراتېگىيە يېڭىلاش يوق. ماختاپ كەتمەي ئېنىق ئېيتاي: HexClaw «بالا ۋەزىپە تارقىتىش → نىشانغا سېلىشتۇرۇپ كەمچىلىك كۆرۈش → كېيىنكى ئايلانما قوشۇش»تىن ئىبارەت قاتلاملىق پارچىلاش ۋە قايتا پىلانلاش، plan-execute-replan. پەقەت كەمچىلىكنى تولدۇرىدۇ، كۆپ نامزات ئارىسىدا نومۇر بىلەن ئەڭ ياخشىسىنى تاللىمايدۇ، كەينىگە قايتىش ۋە شاخ كېسىش يوق. شۇڭا Tree of Thoughts، Yao قاتارلىقلار، NeurIPS 2023، ياكى MCTS كە ئوخشاش ھەقىقىي ئىزدەش دەرىخى ئەمەس. ئۇنداق دېيىش ئاشۇرۇۋېتىش. ئەمما «بىر توپ چىقىرىش → مۇستەقىل باھالاش → كەمچىلىككە قاراپ يەنە چىقىرىش» قۇرۇلمىسى ھەقىقىي. engine/orchestrate.go دىكى orchestrate شۇنداق يېزىلغان. ئومۇمىي goal ۋە max_rounds > 1 بېرىلسە، بىر توپ ئىش تارقىتىپلا توختىمايدۇ؛ ھەر fan-out، پاراللېل بالا Agent تارقىتىشتىن كېيىن مۇستەقىل «نازارەتچى» ئومۇمىي نىشانغا سېلىشتۇرۇپ يېتەرلىكمۇ دەپ باھالايدۇ، يېتەلمىسە نىشانلىق كېيىنكى ئايلانمىنى قوشىدۇ:

1// 每轮 fan-out 后由监工对照总目标评判——未达成则补派针对性子任务进下一轮，2// 直至达成 / 无后续 / 触顶轮数 / 预算耗尽。3for round := 1; round <= maxRounds; round++ {4 allCollected = append(allCollected, o.runRound(...)...) // 并行派活、收结果5 if round == maxRounds || runCtx.Err() != nil || goal == "" {6 break // 触顶 / 墙钟到点 / 无目标7 }8 dec := o.supervise(runCtx, goal, allCollected) // 独立监工评判9 if dec.Done || len(dec.Next) == 0 { break } // 监工说够了 / 没新活10 roundSubtasks = dedupSubtasks(dec.Next, allDispatched) // 去重后进下一轮11}

بۇ يەردىكى ئاچقۇچلۇق لايىھە، بۇ مۇنازىرىلەردە كۆپ تەكىتلەنگەن تۆمۈر قائىدە: maker بىلەن checker ئايرىم بولۇشى شەرت. كود يازغان Agent بىلەن «تاماممۇ»نى بەلگىلەيدىغان Agent بىر بولماسلىقى كېرەك، چۈنكى مودېل ئۆزىگە نومۇر بەرگەندە بەك كەڭچىل. بۇ تەجرىبە سۆزىلا ئەمەس: Google DeepMind ICLR 2024 دە سىرتقى قايتما ئۇچۇرسىز LLM ئاساسەن ئۆزىنى تۈزىتىپ بولالمايدىغانلىقىنى تەكشۈرگەن؛ بەزىدە بىر ئايلانما «ئۆزىنى تۈزىتىش»تىن كېيىن تېخىمۇ ناچار، Huang قاتارلىقلار. HexClaw نازارەتچىسى subagent_supervisor.go دىكى قورالسىز، پەقەت باھالايدىغان مۇستەقىل بالا Agent، ئىشلىگۈچى بىلەن بىر رول ئەمەس. ئۇ پەقەت JSON قايتۇرىدۇ: {"done": true} توختىتىدۇ، ياكى {"done": false, "next": [...]} يېڭى ئىش قوشىدۇ. مەغلۇپ بالا ۋەزىپىلەرمۇ نازارەتچىگە ئېنىق بىلدۈرۈلىدۇ؛ بولمىسا ئۇ پەقەت «مۇۋەپپەقىيەتلىك يېرىم»نى كۆرۈپ خاتا تامام دېيىشى ئاسان.

قايتا-قايتا تىلغا ئېلىنغان بىر كۆزىتىش: نۇرغۇن Agent ئىجرا جەريانىدا ئىشتىن چىقىدۇ، يىلتىز سەۋەبى توختاش شەرتى يوق. يا تۈزەلگەندىن كېيىن يەنە ئۆزگەرتىپ بۇزىدۇ، يا تۈزەلمەي تامام دەپ يالغان دەيدۇ. HexClaw بۇ ھالقىنىڭ توختاش شەرتىنى بىر قاتار قاتتىق دەرۋازىغا قۇلۇپلىغان:

  • ئايلانما دەرۋازىسى: نازارەتچى قايتما ھالقىسى ئەڭ كۆپ 3، بىرىنچى ئايلانما ۋە ئەڭ كۆپ 2 قوشۇمچە ئايلانما. يەرلىك كىچىك مودېلنىڭ قۇرۇلمىلىق JSON قارارى ئىشەنچسىز بولغاچقا 1 قىلىنىدۇ، يەنى تەكرارلاش تاقىلىپ ھەمىشە بىر ئايلانما.
  • تاشقى ۋاقىت دەرۋازىسى: پۈتۈن orchestrate، كۆپ ئايلانما ۋە بىرىكتۈرۈشنى قوشۇپ، 5 مىنۇت ئومۇمىي ۋاقىت چېكى بار. ۋاقىت توشسا بارلىق ئىجرا بولۇۋاتقان بالا Agent بىكار قىلىنىدۇ، ئادەم بىكار ساقلاپ قالمايدۇ.
  • سان دەرۋازىسى: بىر قېتىم ئەڭ كۆپ 8 بالا ۋەزىپە، پاراللېل چەك بۇلۇتتا 8، يەرلىكتە 2.
  • پۈتۈن تارماق دەرىخىنىڭ backstop چېكى: بىر ھاسىل قىلىش دەرىخىدە چوڭقۇرلۇق ۋە ئايلانمىلار ئارا يىغىندا ئەڭ كۆپ 128 بالا Agent. تولۇق دەرەخ 8 + 8×8 = 72 بالا، نازارەتچىنىڭ كۆپ ئايلانما قوشۇشى بىلەن ئاسانلا نەچچە يۈز مودېل چاقىرىشقا يېتىدۇ. 128 «ئۇۋىلاش × كۆپ ئايلانما» پارتلىشىغا قاتتىق چەك؛ ساھەدىكى مىڭلىق ئومۇمىي زاپاس چەككە سېلىشتۇرغاندا يەككە كومپيۇتېرغا يېقىن.
  • ئۆلۈك ھالقا زاپىسى: نازارەتچى چىقىرىشى پارس بولمىسا done دەپ ھۆكۈم قىلىنىدۇ. «ھۆكۈمچىنى چۈشەنمىدىم» دەپ مەڭگۈ ئايلىنىشقا يول يوق. بالدۇر توختىسا بولىدۇ، قۇرۇق ئايلىنىشقا بولمايدۇ.

چىقىممۇ ئېنىق ۋە قەستەن چەكلەنگەن: ھەر قوشۇمچە ئايلانمىدا بىر نازارەتچى مودېل چاقىرىشى ۋە بىر توپ بالا Agent چاقىرىشى بار. شۇڭا ئايلانما 3 تە قۇلۇپلانغان. «ئەڭ كۆپ ئىككى قېتىم قايتا ئىشلەش» ئارقىلىق «تاڭ ئاتقۇچە قۇرۇق كۆيدۈرمەسلىك» يەككە كومپيۇتېر كۆلىمىدە مۇۋاپىق ھېساب.

ئەمما ھېسابنىڭ كۆپ نەزەردىن ساقىت بولىدىغان يەنە يېرىمى بار: كۆپ ئايلانما چىقىمى بىر ئايلانما چىقىمىنى ئايلانما سانىغا ئاددىي كۆپەيتىش ئەمەس. ھەر نازارەتچى ۋە بالا Agent نىڭ ئالدىدىكى مۇقىم prefix ئوخشاش: system prompt، دائىمىي Rules ۋە ئومۇمىي نىشان سۆزمۇسۆز ئۆزگەرمەيدۇ. يۇقىرى ئېقىمدا prompt cache ياكى prefix cache ئوچۇق بولسا، Anthropic prompt caching ياكى vLLM نىڭ PagedAttention KV ئىچكى ساقلىغۇچ باشقۇرۇشى ئۈستىدىكى مۇستەقىل automatic prefix caching، ئاساسىي مېخانىزم Kwon قاتارلىقلار، SOSP 2023، prefix نىڭ KV سى تۇنجى ھېسابتىن كېيىن ساقلىنىپ، كېيىنكى ئايلانما بىۋاسىتە ماس كېلىدۇ. يېڭى token تولۇق باھا، ماس كەلگەن قىسىم ناھايىتى تۆۋەن ئېتىبار باھاسى. ھەقسىز ئەمەس: Anthropic cache ئوقۇش تەخمىنەن 0.1×، يېزىش 1.25×، بىر قېتىم ماس كەلسە چىقىم قايتىدۇ. مۇقىم دائىمىي تېكىست قانچە ئۇزۇن، ماس كېلىش قانچە يۇقىرى بولسا، ھەقىقىي چىقىم «تېكىست token × ئايلانما»دىن شۇنچە يىراق. بۇ ئالدىنقى ماقالىدىكى دائىمىي قاتلامنى سۆھبەت بېشىدا مۇقىم سۈرەتكە توڭلىتىشنىمۇ چۈشەندۈرىدۇ: ھەر ئايلانما مۇقىم بولۇش ئۈچۈنلا ئەمەس، prefix سۆزمۇسۆز ئوخشاش بولۇپ cache كە ماس كېلىشى ئۈچۈن. تېجىلىدىغىنى ھەقىقىي تەكرار prefill چىقىمى.

شۇڭا HexClaw دا ھەقىقىي قايتما ھالقا بار: مۇستەقىل ھۆكۈمچى، قايتما ئۇچۇرلۇق تەكرارلاش ۋە قۇلۇپلانغان چىقىشلار. بۇ PPT ئوقلىرى ئەمەس، توختايدىغان كود. ئەمما دائىرىنى توغرا دېيىش كېرەك: ئۇ بىر سۆھبەت ئىچىدىكى چەكلىك ۋەزىپىنى يېقىنلاشتۇرىدۇ، «تامام»نى نازارەتچى بەلگىلەيدۇ؛ fail-open، چۈشەنمىسە بالدۇر توختايدۇ، تېخى ماشىنا قوبۇل قىلىشى ئەمەس. نىشانغا ماشىنا تەكشۈرەلەيدىغان، fail-closed قوبۇل قىلىش قوشقان دائىمىي ھالقا تۆۋەندىكى ④ دە.

③ «ئىجرا قىلغۇچىغا ئىشەنمە»: HexClaw نىڭ مۇستەقىل ھۆكۈمچى ئائىلىسى

بىر ئېنىق ئوخشىتىش بار: maker / checker نىڭ ماھىيىتى Kubernetes دىكى Admission Controller، ھەرىكەت كۈچكە ئىگە بولۇشتىن بۇرۇن مۇستەقىل تەكشۈرۈش. ئاساسىي ئېتىقاد ئىجرا قىلغۇچىغا ئىشەنمە. HexClaw بۇنى بىر ئائىلىگە ئايلاندۇردى؛ «قىلىپ بولدۇم، توغرا قىلدىم» دەيدىغان ھەر يەرگە ئىشلىمەيدىغان، پەقەت نۇقسان ئىزدەيدىغان بىر رول قويۇلدى:

  • يېقىنلىشىش ھۆكۈمچىسى: يۇقىرىقى supervisor، loop توختاش كېرەكمۇ دەپ ھۆكۈم قىلىدۇ.
  • كىرىش ھۆكۈمچىسى: risk_judge.go ۋە ئادەمسىز خەتەر مەسلىھەتچىسى، HexClaw نىڭ Admission Controller ى. ئادەم يوق ئاپتوماتىك سۆھبەتتە ئاقىۋەتلىك ھەرىكەت «تەستىق كېرەك»كە ئۇچرىسا، مۇستەقىل LLM دىن low / medium / high دەرىجە سورىلىدۇ. پەقەت low بىر قېتىم ئۆتىدۇ، باشقىسى fail-closed رەت قىلىنىدۇ. دەرىجە چاقىرىشىغا قەستەن 16 token خامچوت، پەقەت بىر سۆزلۈك قارار، ئەرزان.
  • ئۆزىنى ياخشىلاش ھۆكۈمچىسى: skill_judge.go، LLM-as-judge. ھەر قورال چاقىرىشىدىن كېيىن 10% ئەۋرىشكە بىلەن 0–10 نومۇر بېرىدۇ، 7 دىن تۆۋەن بولسا «ياخشىلاش لايىھىسى» يازىدۇ. ئاچقۇچى مەغلۇبىيەت ھالىتى: ئەۋرىشكە تاللانمىسا، ۋاقىت توشسا ياكى خاتالىق بولسا 10 نومۇر، fail-open. ھۆكۈمچى داۋالغۇشى سەۋەبسىز نۇرغۇن لايىھە چىقارمايدۇ.
  • ئىجرا بىلەن ئاساسلاش: solve مەسىلە يېشىش. K12 دە مەخسۇس تەكشۈرگۈچى بالا Agent پەقەت code_exec ئىشلىتىپ، يېڭى context تا قايتا ھېسابلايدۇ. «ئارىفمېتىكا توقۇلمىسى» دېگەن باش سەۋەب ئېنىق ئىجرا بىلەن توسۇلىدۇ. ئىشەنچسىز ھۆكۈم فۇنكسىيەسىگە ئېنىق ئىجرا قاتتىق دەرۋازىسى قوشۇلىدۇ.
  • توقۇلمىغا قارشى پاكىت تەكشۈرۈش: cron. «ئامبارغا كىرگۈزىمەن» دېگەن ۋەزىپە پۈتۈن ئايلانمىدا knowledge_ingest نى ئەمەلىي چاقىرمىسا، دوكلاتى قانچە مۇۋەپپەقىيەتلىك دېسىمۇ مەغلۇپ. چۈنكى ھېچ نەرسە ساقلانمىغان، «تامام» نەتىجە ئەمەس، توقۇلما.

بۇلارنىڭ ئارقىسىدا بىر ھۆكۈم بار: LLM سۆزلىيەلەيدىغان، ئەمما ئۆزىنى ئالدايدىغان ئىجرا قىلغۇچى. ئۇ داۋالغۇشى، قېتىپ قېلىشى ياكى كود ئىشلىمىسىمۇ ئۆزىگە تولۇق نومۇر بېرىشى مۇمكىن. HexClaw نىڭ چارىسى «مودېلنى تېخىمۇ ئىتائەتچان قىلىش» ئەمەس، ئۆزىنى ئالدايدىغان ھەر جايغا مۇستەقىل گۇمانچى قوشۇش.

④ ئەڭ قىيىن ئىككى يۇقىرى چەك: فورماللاشتۇرغىلى بولىدىغانلىرى تولۇقلاندى، قالغىنى پۈتۈن ساھەنىڭ توسۇقى

بىرسى بۇنى مەن ياخشى كۆرىدىغان بىر فورمۇلاغا يىغغان:

Agent capability = Model × Context × Loop × Evaluation

نۇرغۇن ئادەم Model نى، ئاز ئادەم Context نى ياخشىلاۋاتىدۇ، Loop قا تېگىدىغانلار تېخىمۇ ئاز. ئەمما ھەقىقىي يۇقىرى چەك ئاخىرقى Evaluation ۋە ئۇنىڭ ئۈستىدىكى Goal. ئالدىنقى ئۈچىدە HexClaw نىڭ ھەقىقىي كودى بار. كېيىنكى ئىككىسى ئەڭ قىيىن؛ تولۇقلىغىلى بولىدىغاننى تولۇقلىدىم، ئەمما پۈتۈن ساھەگە تەۋە بىر توسۇقنى راست ئېچىپ كۆرسىتىش كېرەك.

Evaluation نىڭ تورسىز يېرىمى قىلىندى. HexClaw دا eval/runner.go golden باھالاش بار. replay ھالىتى 0 token، ئېنىق بولۇپ، CI دا «كود قايتىشى»نى، پارس، تەكشۈرۈش، يوللاش، ھوقۇق دەرۋازىسى ياكى Skill ئەسلەش بۇزۇلۇشىنى تۇتىدۇ. live ھالىتى EVAL_LIVE=1 ھەقىقىي مودېل كىرگۈزۈپ «مودېل چېكىنىشى»نى تۇتىدۇ. نومۇر دەرۋازىسى نەشر دەرۋازىسى:

1// 评分门 = 发版门：风险 high recall = 100%(fail-closed) ·2// 编译器 replay 全过 · 工具 retrieval 100%。

بۇ Anthropic ۋە OpenAI نىڭ Evals گۇرۇپپىلىرىغا زور بايلىق سېلىۋاتقان ئىشىنىڭ HexClaw نەشرى. Evaluation بولمىسا loop يېقىنلىشالمايدۇ، مودېل قانچە كۈچلۈك بولسىمۇ تاسادىپىي سەيلە قىلىدۇ. Golden نەشر لىنىيەسىدە قايتىش تۇتىدۇ؛ ھەر ئايلانمىنىڭ توردا قوبۇل قىلىنىشىنى HexClaw باشقا مېخانىزم بىلەن تۇتىدۇ. بۇ تېخىمۇ قىيىن ئىككىنچى ئىشقا ئېلىپ كېلىدۇ.

Goal نى فورماللاشتۇرۇش ئەڭ قىيىن. K8s مۇۋەپپەقىيىتىدىكى تۆۋەن مۆلچەرلەنگەن ھەقىقەت etcd ياكى Controller نىڭ ياخشى لايىھەسىلا ئەمەس، كۈتۈلگەن ھالەتنىڭ ماتېماتىكىلىق بولۇشى: replicas: 3، «تامام» نېمە؟ actual == 3. مۈجمەللىك، ئېستېتىكا ياكى «يېتەرلىك بولدى دەپ ئويلايمەن» يوق. شۇڭا Controller ئىسپاتلىغىلى بولىدىغان يېقىنلىشىش قىلالايدۇ، ئادەمسىز ئىجرا شۇنداق ئورنىغا كېلىدۇ.

بۇ توسۇققا قاراپ HexClaw «نىشان»نى ئىككىگە ئايرىدى: مەقسەت، تەبىئىي تىلدا ئىشلىگۈچى Agent قا؛ قوبۇل قىلىش، ماشىنا ھۆكۈم قىلالايدىغان بىر توپ assertion: بۇيرۇق ئىجرا قىلىپ exit 0 كۆرۈش، regex ماسلاشتۇرۇش، JSON مەيدانى تەڭلىكى ياكى rubric نومۇرى بوسۇغىدىن ئۆتۈش. شۇنىڭ بىلەن done پەقەت نازارەتچىنىڭ done: true ى ئەمەس، «بارلىق قوبۇل قىلىش assertion ى ئۆتتى». ئىجرا بولىدىغان قوبۇل قىلىش يېزىلغان نىشان K8s تىكى actual == desired غا ئوخشاش ماشىنا ھۆكۈمىنى ئالىدۇ. دىققەت: بۇ ماشىنا ھۆكۈم قىلالايدىغان done، K8s كە ئوخشاش ئىسپاتلىنىدىغان يېقىنلىشىش ئەمەس. يېزىپ بولمايدىغان ساپ سۇبيېكتىپ نىشانلا LLM ھۆكۈمچىگە قايتىدۇ. بۇ مېخانىزم قەيەرگە قويۇلغان، شۇ بۇ قاتلامدا ئەڭ ئېنىق چۈشەندۈرۈلىدىغان قۇرۇلما.

يۇقىرىدىكى ② سۆھبەت ئىچى تەشكىللىگۈچى نازارەتچى بىلەن «قۇرۇلمىلىق نىشان + ماشىنا قوبۇل قىلىشى» بىر loop ئەمەس، ئىككى. قەستەن ئايرىم ۋەزىپە، ھەتتا مەغلۇبىيەت ھالىتىمۇ ئەكسى:

  • سۆھبەت ئىچى تەشكىللەش ھالقىسى: orchestrate.go + subagent_supervisor.go «قۇرۇق چىقىم»نى توسىدۇ. نازارەتچى چۈشەنمىسە done، fail-open-to-done، بالدۇر توختاشنى تاللايدۇ.
  • نىشان يېتەكچىلىكىدىكى دائىمىي ھالقا: goalloop.go + checker.go + acceptance.go، يېڭى يېزىلغان. «تامامدەك كۆرسىتىش»نى توسىدۇ. Checker باشقا رول، ئەڭ ياخشىسى تېخىمۇ كۈچلۈك مودېل، ③ دىكى ئائىلىنىڭ ئەڭ قاتتىق ئەزاسى. ئاۋۋال ئېنىق قوبۇل قىلىش assertion ى، exit 0، regex ياكى JSON تەڭلىك ئىجرا بولىدۇ. پەقەت ماشىنا ھۆكۈم قىلالايدىغان assertion پۈتۈنلەي يېزىلمايدىغان نىشانلا LLM غا قايتىپ، ئۆزئارا بىردەكلىك كۆپ سانلىق ئاۋازى ئىشلىتىدۇ. self-consistency، Wang قاتارلىقلار، ICLR 2023؛ ئىشەنچ = ئاۋاز بىردەكلىكى. مۈجمەل ياكى خاتا بولسا fail-closed، ئۆتكۈزمەيدۇ.

ئىككىسىنىڭ تاللىشى ئەينەك ئوخشاش: تەشكىللەش ھالقىسى «تېخى تۈگىمىدى»نى قولدىن بېرىپ بالدۇر توختىسىمۇ قۇرۇق كۆيدۈرمەيدۇ؛ دائىمىي ھالقا يەنە بىر ئايلانما ئىجرا قىلسىمۇ «تۈگىدى» دەپ خاتا ھۆكۈم قىلمايدۇ. دائىمىي ھالقىنىڭ سىرتىدا ھەر ئايلانمىدا دىسكىغا يېزىلىدىغان level-triggered ھالەت، goalloop_state.go بار؛ ئۆلتۈرۈلۈش ياكى قايتا قوزغىلىشتىن كېيىن ئالدىنقى ئايلانمىدىن داۋاملىشىدۇ. ئىلگىرىلەش يوقلۇق ۋە داۋالغۇشنى بايقاش بار. توختاش مەنىسى done، capped يۇقىرى چەككە يېتىش، escalated ئادەمگە كۆتۈرۈش دەپ ئايرىلغان؛ قېتىپ قېلىش جىمجىت كېسىش ئەمەس، no_progress / low_confidence / high_risk سەۋەبى بىلەن ئادەمگە قايتۇرۇلىدۇ.

سەمىمىي خۇلاسە: فورماللاشتۇرغىلى بولىدىغانلىرى تولۇقلاندى. قۇرۇلمىلىق نىشان، توردا قوبۇل قىلىش دەرۋازىسى، مۇستەقىل ئۆزئارا بىردەك ھۆكۈمچى، ئىلگىرىلەشسىزلىك/داۋالغۇش بايقاش، level-triggered داۋاملاشتۇرۇش ۋە قېتىپ قالغاندا ئادەمگە كۆتۈرۈشنىڭ ھەممىسى ئىجرا بولىدىغان ھەقىقىي كود. ئەمما ئىنژېنېرلىق تولدۇرالمايدىغان بىر بوشلۇق بار: كونترول قىلىنىدىغان نەرسە LLM دېگەن «ئېھتىماللىق بۇلۇتى». «پاراللېللىق مەسىلىسىنى تۈزەت» دېگەن بىر گەپنى بۈگۈن باشقا، ئەتە باشقا يېزىدۇ، idempotent ئەمەس ئىجرا قىلغۇچى. شۇڭا ئىجرا بولىدىغان قوبۇل قىلىش يېزىپ بولمايدىغان ساپ سۇبيېكتىپ نىشاننىڭ يېقىنلىشىشىنى يەنىلا ئىسپاتلىغىلى بولمايدۇ. ئايلانما چېكى چىقىم زاپىسى، يېقىنلىشىش ئىسپاتى ئەمەس. نازارەتچىنى كىم نازارەت قىلىدۇ؟ دېگەن كلاسسىك سوئال يەنىلا بار. HexClaw ئىسپاتلىغاندەك قىلمايدۇ: ماشىنا ھۆكۈم قىلالىسا ماشىنا، ئېنىق بولمىسا كۆپ ھۆكۈمچى، ئۆزئارا بىردەكلىك ۋە fail-closed بىلەن تارايىتىش، يەنە ئېنىق بولمىسا توختاپ ئادەمگە بېرىش. «ئۆزلۈكىدىن قىلىۋاتقاندەك» بولۇشنىڭ ئورنىغا «قاچان ئادەم چاقىرىشنى راست بىلىش».

يەنە بىر ھالقىنى قەستەن تاقىمىدىم؛ قىلالمىغان ئەمەس، لايىھە تاللىشى. ئۆزىنى ياخشىلاش ھۆكۈمچىسى تۆۋەن نومۇر بەرسە، پەقەت <skills directory>/.drafts/ غا لايىھە يېزىدۇ. سىز تەكشۈرۈپ ئۆزىڭىز mv قىلغاندىلا كۈچكە ئىگە. «مەغلۇبىيەت → لايىھە → ئادەم تەكشۈرۈش → ساقلاپ قالدۇرۇش» زەنجىرى بىر قېتىملىق ئويلىنىش ئەمەس، قايتا ئىشلىتىدىغان ماھارەت لايىھىسى يازىدۇ. بۇ Voyager، Wang قاتارلىقلار، 2023، نىڭ «Agent ئۆز ماھارەت كۈتۈپخانىسىغا يېڭى ماھارەت ئۆستۈرۈش» ئۆزلۈكىدىن تەرەققىي قىلىشىغا يېقىن. پەرقى ئاخىرقى «ئۆزلۈكىدىن كۈتۈپخانىغا يېزىش»نى «ئاۋۋال لايىھە، ئادەم كۆرگەندىن كېيىن كۈچكە ئىگە»گە قۇلۇپلىدىم؛ AI ئۆزى ئەسلەتمە باشقۇرۇشىمۇ consent دەرۋازىسىدىن ئۆتىدۇ.

مەن بۇ يەردە ئادەم كۆرەلەيدىغان، ئۆزگەرتەلەيدىغان ۋە قايتۇرالايدىغان بىر يوچۇق قالدۇرۇشنى، loop نىڭ ئۆز ئىقتىدارىنى جىمجىت ئۆزگەرتىشىدىن ئەۋزەل كۆرىمەن. Osmani «ئاسان بولسۇن دەپ قول قويۇۋېتىش»نىڭ چىقىمىنى ئىككى خىل ئاتىغان: چۈشىنىش قەرزى، ئۆزى چۈشەنمىگەن نەرسىنى يەتكۈزۈش؛ بىلىشتىن ۋاز كېچىش، ئىنژېنېر پەقەت «باشلا» كۇنۇپكىسى باسىدىغان ئادەمگە ئايلىنىش. ئادەمسىز ئىجرا بولۇۋاتقان loop، ئادەمسىز خاتالىق قىلىۋاتقان loop مۇدۇر.

بۇ قورقۇتۇش ئەمەس: 2025-يىلى ئىيۇلدا Replit نىڭ AI كودلاش Agent ى «كود توڭلىتىلغان، رۇخسەتسىز ئۆزگەرتمە» دەپ ئېنىق بۇيرۇلغان تۇرۇپ SaaStr نىڭ ئىشلەپچىقىرىش سانلىق مەلۇمات ئامبىرىنى ئۆچۈرگەن، 1200 دىن ئارتۇق باشقۇرغۇچى ۋە 1190 دىن ئارتۇق شىركەت سانلىق مەلۇماتى. كېيىن «كەينىگە ياندۇرغىلى بولمايدۇ» دەپ يالغان ئېيتقان، قارشى تەرەپ قولدا ئەسلىگە كەلتۈرگەندىلا ئاشكارىلانغان. Replit كېيىن تەرەققىيات ۋە ئىشلەپچىقىرىش ئامبىرىنى ئۆزلۈكىدىن ئايرىش، پەقەت ئوقۇيدىغان planning-only ھالەت ۋە ئىشەنچلىك قايتۇرۇش قوشقان. بۇ دەل HexClaw باشتىن قۇلۇپلىغان دەرۋازىلار: خەتەرلىك ھەرىكەت كىرىش تەكشۈرۈشىدىن، ئۆزىنى ياخشىلاش پەقەت لايىھە، cron دا ئۆزىنى ئۆستۈرۈش يوق. شۇڭا تەكشۈرۈش ھالقىسىنى بەرمەيمەن.

تۆت قاتلامنى ئۈستىلەش: نېمىنى بەردىڭىز، نېمىنى بەرمىدىڭىز؟

كەينىگە قارىغاندا ئەڭ ئېنىقى «يەنە بىر مودا سۆز قوشۇلدى» ئەمەس، ھەر بىر قاتلام سىرتقا كېڭەيگەندە بىر قاتلام قارار ھوقۇقى بېرىلىدۇ. كۈندىلىكتە سىزنىڭ قاتنىشىش چاستوتىڭىز تۆۋەنلەيدۇ، سىستېمىنى لايىھەلەش قىيىنلىقى ۋە ئاقىۋىتى يۇقىرىلايدۇ:

  • Prompt: ئىپادە ھوقۇقى، بۇ جۈملە قانداق ئېيتىلىدۇ.
  • Context: ئۇچۇر تاللاش ھوقۇقى، ئۇ نېمىنى كۆرۈشى كېرەك.
  • Harness: جەرياننى كونترول قىلىش، قانداق ماڭىدۇ، چېگراغا يەتكەندە ئۆتكۈزۈلەمدۇ.
  • Loop: باشلاش ۋە قوبۇل قىلىش، قاچان يولغا چىقىدۇ، بىر ئايلانما لاياقەتلىكمۇ، قاچان تامام.

«بۇ سۆزلەر ساختا ئۇقۇم ئوينىتىشمۇ؟» دېسەك، ھۆكۈمۈم زاپچاس يېڭى ئەمەس، ئورنى يېڭى. بالا Agent، Skill، ئەسلەتمىنى ساقلاش ۋە مۇستەقىل ھۆكۈمچى Harness تا بار ئىدى، Loop يېڭى زاپچاس كەشىپ قىلمىدى. ئۆزگەرگىنى ئۇلار باشقا بىر ۋاقىت قۇرۇلمىسىغا قويۇلدى: «بىر تاماق چىقىرىش»تىن «بىر رېستوران ئېچىش»قا. ئورۇن ئۆزگەرسە ئىنژېنېرلىق جاۋاب بېرىدىغان سوئالمۇ ئۆزگىرىدۇ، بۇ يېتەرلىك؛ ئالغا ئىلگىرىلەش ئۈچۈن چوقۇم يېڭى زاپچاس كەشىپ قىلىش شەرت ئەمەس.

ئەمما تۆت قاتلامدا بېرىلمىگەن، بېرىشكە بولمايدىغان بىر نەرسە بار: مەسئۇلىيەت. HexClaw نىڭ لايىھە خاراكتېرى ھەر بېرىلگەن ھالقىدا بىر يوچۇق قالدۇرۇش: ئەسلەتمە git diff قىلىنىدۇ، سكرىپت كۆرگىلى بولىدىغان sandbox كودى، خەتەرلىك ھەرىكەت كىرىش دەرۋازىسىدىن ئۆتىدۇ، ئۆزىنى ياخشىلاش پەقەت لايىھە، يېقىنلىشىشتا قاتتىق توختاش شەرتى بار.

كونترول نەزەرىيەسىدىكى ئەڭ ئاددىي فورمۇلا Control = Goal − Observed State. كۆزىتىلگەن ھالەت ئۆلچەنمىسە كونترول يوق؛ نىشان ئېنىق بولمىسا يېقىنلىشىش يوق. شۇڭا ھەقىقىي سوئال «قايسى مودېل كۈچلۈك» ئەمەس، ئەڭ جەلپ قىلمايدىغان، ئەمما ئەڭ قىيىن «تامام دېگەن نېمە؟». Kubernetes بۇنىڭغا فورمال spec بىلەن يىگىرمە يىلغا يېقىن جاۋاب بېرىۋاتىدۇ. AI تەرەپتە HexClaw نىڭ جاۋابى: ئىجرا بولىدىغان قوبۇل قىلىش يېزىشقا بولىدىغان نىشاندا قاچان توختاشنى ماشىنا ھۆكۈم قىلالايدۇ. قالغان ساپ سۇبيېكتىپ نىشاننى فورماللاشتۇرۇش ۋە ئېھتىماللىق بۇلۇتى ئىجرا قىلغۇچىنىڭ ئىسپاتلىنىدىغان يېقىنلىشىشى پۈتۈن ساھەنىڭ توسۇقى، مەن ئۇنى ئوچۇق قويدۇم.

كەلگۈسىدىكى ئىنژېنېر بەلكىم فۇنكسىيە ئەمەس loop يازار؛ يەنە بىر قەدەم ئۆتسە نىشان ۋە تەكشۈرۈش يازار. ئۇ مودېل بىلەن قانداق سۆزلىشىشنى ئەمەس، ئىشەنچسىز ئىجرا قىلغۇچىنى داۋاملىق قايتما ئۇچۇر بىلەن ئېنىق بىر نىشانغا قانداق مۇقىم يېقىنلاشتۇرۇشنى تەتقىق قىلىدۇ.

بۇ ماقالە تۆت قاتلامنى تۇتاشتۇرغان ئاساسىي پروگرامما، ھەر قاتلامغا ماس چوڭقۇر ماقالە ئۇلانغان. تېخى ئايرىم سۆزلەنمىگەن بىر پارچە قالدى: سىز تەشەببۇسكارلىق بىلەن بەرگەن ماتېرىيال، ھۆججەت ۋە كود، يەنى بىلىم ئامبىرى RAG زەنجىرى. ئۇ ئەسلەتمە بىلەن ئوخشاش يەرلىك ئىزدەش ئاساسىنى ئورتاق ئىشلىتىدۇ، ئەمما پۈتۈنلەي باشقا «ئەستە تۇتۇش»قا ئايلانغان. ئۇ كېيىنكى ماقالىنىڭ ئىشى.
