HexClaw’s Skills over MCP: Where to Lock Trust When Tools Bring Their Own Playbook

From 10 MCP entries quarantined after HTTP 404 to a 12-file bundle check: HexClaw’s local supply-chain defense, layer by layer

From 10 MCP entries quarantined after HTTP 404 to a 12-file bundle check: how HexClaw builds a local supply-chain defense

78 skills × 59 MCPs (49 pinned, 10 quarantined) × --with dependency allowlist × offline BOM and fail-closed credential box

This Tuesday (November 24), during MCP's second-anniversary week, Anthropic pushed Skills over MCP into public Beta. First, let's clear up an easily misread phrase: like HTTP over TLS, the over here means distributing Skills over the MCP protocol — the server publishes a workflow, and the client reads SKILL.md and its companion files when needed.

One detail in the release notes deserves a closer look. According to the November 24 announcement, it is on by default for individual plans (Pro / Max / Ultra), must be enabled by an administrator for Team, and was still pending for Enterprise at the time. Tools now come with their own “playbooks,” but which version gets used after you connect them still depends on the host.

How much does that gate matter? We found out while curating HexClaw's 59 MCP marketplace entries. Checking the declared package names against the official npm registry, 10 returned HTTP 404. google-drive, postman, wolfram-alpha, and ffmpeg-video-processor were all names recorded in the catalog at the time. Picture this: casually set @latest for a local Agent, and the bytes you get on the next launch may already be a different version.

Connecting tools is no longer hard; SDK wrappers keep getting smoother. The real challenge, as the capability marketplace grows, is keeping your Agent from running exposed among wild packages and floating scripts.

Core judgment of this article:

1. Skills over MCP expands the review surface from tool descriptions to remote playbooks. A Skill with a static manifest requires checking file digests. The host must also decide which version of the playbook to adopt, while where local dependencies come from depends on the installation chain.

2. Local marketplace admission checks must be welded into both the type system and CI. In the HexClaw marketplace, 49 pinned MCP entries record exact versions, source declarations from official registries, and hash metadata. Ten entries were placed in quarantined because their package-name lookups returned 404. PyPI allows at most one declared --with group per entry, and a Skill directory bundle is checked file by file against its manifest of 12 files.

3. Release references and offline snapshots let the desktop know which catalog version it holds. Admission checks can verify the main package version and declaration. Which artifact the package manager actually downloaded, and which transitive dependencies it resolved, require that installation's own record.

30-second version:

This article examines Anthropic's Skills over MCP (SEP-2640) extension and how HexClaw (hexclaw-hub v0.1.1 + hexclaw v0.5.2 + hexagon v0.6.0) runs its supply-chain defense against three real sets of objects: 10 MCP entries quarantined after HTTP 404, the single PyPI --with dependency constraint for weather, and the 12-file SHA-256 bundle of homework-pdf 1.1.8. It then closes on offline catalog refresh, fail-closed credential boxes, and underlying MCP Resources/Prompts multimodal isolation. It also states plainly: the HexClaw marketplace pins catalog references to Hub release tags by default and has not yet wired up MCP's remote Skills extensions (skills/list and related endpoints).

Where exactly does the trust surface widen once Skills over MCP lands?

Connect the industry timeline of the past month and the direction is clear. On October 22, 2026, the Linux Foundation's Agentic AI Foundation (AAIF) formally brought Agent Skills under governance, placing them in the same open-standard landscape as MCP; then on November 24, Anthropic launched Skills over MCP (specification SEP-2640, io.modelcontextprotocol/skills), publicly testing it in Claude and Claude Code (2.1.331+) together with first-wave ecosystem services including Shopify, HubSpot, and Atlassian.

This design targets a real pain point. Early MCP integrations felt like being handed a box of screwdrivers with no assembly manual: some clients dumped the JSON Schemas of dozens of tools into context at once, burning tokens and leaving the model lost in parameter details. Skills over MCP takes a restrained approach — the client first sees which Skills are available through lightweight metadata endpoints (skills/list, skills/get), then reads SKILL.md and companion files on demand through MCP's existing Resources primitive when a relevant task comes up. The server can update the playbook; after the client discovers a new version, it loads it under the host's verification and approval rules. The industry calls this Progressive Disclosure: unused Skill bodies no longer take up context.

The problem sits on the other side of the coin. In April 2025, security research team Invariant Labs disclosed MCP Tool Poisoning and Rug-Pull attacks. Back then, what needed review was the tool description and its changes. Now a playbook sits alongside the tool, so the host's review surface expands to the Skill body and its companion files.

To be fair, Anthropic hasn't left this wide open either. Under SEP-2640, a Skill with a static manifest lists file URIs, byte counts, and SHA-256 digests. For dynamic resources, a prior approval cannot cover files generated later. In Manual and acceptEdits modes, Claude Code offers Allow this version, tying approval to that specific file version; in auto mode, a classifier decides whether to load it. Claude Code skips inline shell commands from remote MCP Skills, and the PreSkillShellCommand hook added in v2.1.332 covers inline commands about to execute. How third-party MCPs are installed locally, whether the catalog remains viewable offline, and how secrets are stored still depend on the host's own implementation.

That's why, when we built the Skill and MCP marketplace in HexClaw, we pinned the default catalog reference to a release version. The two approaches agree on packaging and on-demand loading, but differ clearly in who controls the pace of change and which layer carries the defense:

Skill packaging form

Anthropic Skills over MCP (SEP-2640 remote publishing): The MCP server hosts SKILL.md and its companion files, read on demand via MCP Resources

HexClaw current architecture (marketplace catalog and local install): A separate marketplace repo hexclaw-hub hosts single files and directory bundles (bundle.json); bundle installation selects candidates from the factory package or the Hub

Update control

Anthropic Skills over MCP (SEP-2640 remote publishing): The client reads new versions on discovery. The static manifest provides per-file SHA-256; a file change invalidates saved approvals for that version.

HexClaw current architecture (marketplace catalog and local install): The official default pins to Hub release tag v0.1.1. Explicit configuration can specify other sources or references.

Drift and offline protection

Anthropic Skills over MCP (SEP-2640 remote publishing): Reading new files reaches the remote. Verified content can be cached under host rules; a manually saved approval binds to this version's file manifest.

HexClaw current architecture (marketplace catalog and local install): Bundle installation checks length and SHA-256 file by file. Two snapshots of about 52 KiB each ship with the binary, keeping the catalog browsable offline.

Governance boundary and cost

Anthropic Skills over MCP (SEP-2640 remote publishing): Teams require administrator enablement. In auto mode a classifier decides whether to load; tool calls still follow their own permission policies.

HexClaw current architecture (marketplace catalog and local install): The official default catalog updates its reference and embedded snapshot with each release. An enabled Skill only becomes usable after the new version is installed and the runtime refresh succeeds.

For a desktop Agent running on the user's own machine, I prefer pinning the default catalog to a release version. That way, when you look back to check “which version was installed today,” there is a catalog and digests to verify against. Below, following the data flow, we unpack HexClaw's four layers of defense: marketplace admission, installation checks, offline sync, and the protocol foundation.

Gate one: of 59 MCPs, why are 49 pinned and 10 quarantined?

Lay out the 59 MCP entries and the structure is no mystery: 49 are pinned (37 npm packages via npx plus 12 PyPI packages via uvx), and 10 sit in the quarantined zone. Open hexclaw-hub/mcp-registry.json and you'll find the quarantine_reason of all 10 quarantined entries reads declared npm package returned HTTP 404 — so uniform it's almost funny.

Why not just delete those 10 entries from the JSON and be done with it? Simple: if you quietly remove them, two months later someone curating the list may copy the same repository names back in, stepping on the same 404 — or worse, a name-squatted package. Keeping the entries explicitly, marking status: "quarantined", and having the validation script hard-require that “quarantined entries must not carry an artifact, and must never masquerade as verified packages” amounts to nailing a tombstone into the marketplace manifest, permanently reminding everyone that this ground once collapsed.

Blocking in the marketplace repo's Python script is not enough; the Go client needs a second lock at runtime. In hexclaw/skill/hub/mcp_artifact.go, we use a classic type-boundary trick — wrapping the raw McpServerMeta in a ValidatedMCPServer whose internal field is unexported. Every entry point that installs MCPs from the marketplace (catalog validation, CLI, API, resource lifecycle, and the built-in install Skill) must first pass through ValidatePinnedMCPServer to obtain this read-only projection, then assemble it into the generic runtime mcp.ServerConfig (manually configured custom MCPs use a separate general entry point and do not bypass the marketplace pinning channel):

// hexclaw/skill/hub/mcp_artifact.go:19, 43-82 (excerpt) type ValidatedMCPServer struct { meta McpServerMeta }
func ValidatePinnedMCPServer(meta McpServerMeta) (ValidatedMCPServer, error) { if meta.Status == "quarantined" { reason := strings.TrimSpace(meta.QuarantineReason) // ... fall back to a default message if reason is empty return ValidatedMCPServer{}, fmt.Errorf("条目 %q 已隔离: %s", meta.Name, reason) } if meta.Status != "pinned" || meta.Artifact == nil { return ValidatedMCPServer{}, fmt.Errorf("条目 %q 缺少 pinned artifact", meta.Name) } a := *meta.Artifact // ... package validity and PyPI constraint pre-checks omitted switch a.Ecosystem { case "npm": // ... check npx, exact SemVer, official registry and 64-byte sha512 SRI exactSpec = a.Package + "@" + a.Version for _, arg := range meta.Args { if arg == "-p" || arg == "--package" || arg == "--registry" || strings.HasPrefix(arg, "--package=") || strings.HasPrefix(arg, "--registry=") { return ValidatedMCPServer{}, fmt.Errorf("npx 条目不得注入额外 package 或 registry") } } // ... case "pypi": see next section } }

Look closer: an npm entry must satisfy five conditions at once to pass: the launch command is npx; the version matches an exact SemVer regex (rejecting ^, ~, and latest, e.g. @modelcontextprotocol/server-filesystem@2026.7.10 and @modelcontextprotocol/server-github@2025.4.8); source_registry is nailed to https://registry.npmjs.org; integrity decodes from base64 to exactly 64 bytes of sha512- SRI; and the Args array finally passed to the child process must contain package@version verbatim, while -p, --package, and --registry are all blocked. What's checked here is the artifact declaration and launch arguments in the catalog.

This discipline also catches up with the marketplace repo itself. The header of hexclaw-hub/scripts/validate-mcp-registry.py records an old debt: early credential-injection contracts were maintained by hand — Redis was miswritten as env, MongoDB and MySQL had wrong environment variable names, and SQLite once even pointed at a delisted npm package (now moved to PyPI and pinned as mcp-server-sqlite==2025.4.25). Today the script nails three sets of gates into CI: lines 101–172 verify the command allowlist, shell-danger characters, exact versions, and hash metadata for all 59 MCPs one by one; lines 206–252 add credential and launch-argument regression assertions for the five database representative services that had burned us before (sqlite, mysql, redis, mongodb, postgres); lines 82–98 also sweep the repo's GitHub Actions workflows — external Actions must be referenced by a 40-character commit SHA, runners must not use ubuntu-latest, and scripts must not contain go install ...@latest. Lock the front door only after securing your own build pipeline.

The hardest part of pinning isn't the main package — it's the gap opened by --with

Pinning the main package on paper is easy; run it in the Python ecosystem and the first real conflict pops up immediately. The protagonist is weather, the seemingly most harmless weather service in the marketplace.

We pinned the main package hard at mcp_weather_server==0.6.1. Upstream on PyPI, the SDK only had a lower bound: mcp[cli]>=1.12.0. In the November 1 Linux acceptance run, the package manager resolved SDK 2.3.0, and importing McpError at startup raised an ImportError. HexClaw added <2 to this marketplace entry and passed it through --with to uvx, leaving the original main-package version unchanged. The launch command was uvx --with "mcp[cli]>=1.12.0,<2" --from mcp_weather_server==0.6.1 python -m mcp_weather_server. Re-verified through the app installation API on November 2: the client listed 8 tools, with 0 business calls.

This immediately became an engineering dilemma. Cut off --with altogether and the install entry can no longer carry compatibility constraints for the weather service. Let any extra dependency in, and even the tightest main-package pin can't hold up against one more open door.

Our trade-off: open exactly one precisely declared channel, with no hardcoded weather special case in the general validator. We added an optional scalar field dependency_constraint to MCPArtifact, and both mcp_artifact.go and the marketplace CI validation script check that the declaration, argument, and value correspond one to one:

// hexclaw/skill/hub/mcp_artifact.go:95-116 (single PyPI dependency constraint and blocked wild sources) withCount := 0 for i, arg := range meta.Args { // only accept a dependency constraint explicitly declared in metadata and exactly bound if arg == "--with" { if withCount != 0 || a.DependencyConstraint == "" || i+1 >= len(meta.Args) || meta.Args[i+1] != a.DependencyConstraint { return ValidatedMCPServer{}, fmt.Errorf("uvx 条目不得注入额外 dependency source") } withCount++ constraintArgument = i + 1 continue } if arg == "--with-editable" || arg == "-r" || arg == "--requirements" || arg == "--index-url" || arg == "--extra-index-url" || arg == "--find-links" || strings.HasPrefix(arg, "--with=") || strings.HasPrefix(arg, "--requirements=") || strings.HasPrefix(arg, "--index-url=") || strings.HasPrefix(arg, "--extra-index-url=") || strings.HasPrefix(arg, "--find-links=") { return ValidatedMCPServer{}, fmt.Errorf("uvx 条目不得注入额外 dependency source") } } if a.DependencyConstraint != "" && withCount != 1 { return ValidatedMCPServer{}, fmt.Errorf("uvx 条目不得注入额外 dependency source") }

Look closer and there's an easy-to-miss safeguard: line 103 records constraintArgument = i + 1, and when the main-package argument is checked later (line 123), that index is deliberately skipped (i != constraintArgument). Otherwise someone could write uvx --with mcp_weather_server==0.6.1 python, slipping the main package into the constraint slot to run an arbitrary interpreter command, and a naive string-contains check would be fooled. The marketplace script validate-mcp-registry.py:181-196 uses 11 negative cases to nail down undeclared and duplicate --with, direct URLs, local paths, bare package names without versions, --with= concatenation, private indexes, and main-package misplacement.

But let's be honest: does reaching this point mean you're completely safe? Far from it. In the structure comment at hexclaw/skill/hub/hub.go:42-45, we wrote the plain truth ourselves: Integrity is native admission metadata from the official registry; it does not prove every transitive dependency byte the package manager eventually pulled, and it is not an endorsement that "this package is absolutely trustworthy and safe." mcp[cli]>=1.12.0,<2 only frames the direct dependency in a compatible range; resolution of second- and third-level transitive dependencies still belongs to uvx / npx. Knowing that boundary clearly matters far more than pretending a full-chain lockfile exists.

From single file to directory bundle: how does the only one of 78 Skills, homework-pdf, resist tampering?

After 59 MCPs, let's look at the 78 Skills. Of those 78 entries (including public community entries adapted for HexClaw scenarios with separate source attribution), 77 are still single-file Markdown; only homework-pdf 1.1.8 has evolved into a multi-file directory bundle. It follows the Agent Skills form of SKILL.md plus companion files, with HexClaw's bundle.json describing the whole package.

The reason is practical: to get an Agent to reliably produce a publication-quality homework walkthrough PDF, a few hundred words of Markdown prompt simply can't hold the layout and field contract steady. Open hexclaw-hub/skills/homework-pdf/bundle.json and you'll find 12 files listed: the main instruction SKILL.md, 3 Typst layout templates (including the header/footer assets/pdf-chrome.typ shared with general documents), 1 input/output JSON Schema (assets/report.schema.json), 1 profile, 4 example files, 1 contract reference document, and 1 LICENSE. Its SKILL.md (lines 44–46) draws a hard boundary: the Typst components only handle layout — they do not identify problems, download resources, install dependencies, or call models on their own; files sitting in a directory do not mean the templates have entered the runtime, since taking effect goes through the host's shared Skill lifecycle and capability receipts.

But once a Skill goes from 1 file to 12, the install chain has more to manage: were all files downloaded? Are the manifest paths usable? Does the upstream response length match the manifest? On Hub downloads, PackageSource puts these checks into the candidate package's staging phase.

// hexclaw/skill/hub/skill_bundle.go:72-103 (bundle semantic digest + path traversal guard + per-file SHA-256, excerpt) if manifest.SkillID != name || manifest.Version != meta.Version || manifest.ContractVersion != 1 { return "", nil, fmt.Errorf("skill bundle catalog identity mismatch") } if meta.BundleSHA256 != "" { digest, err := manifest.SemanticDigest() if err != nil { return "", nil, err } if !strings.EqualFold(digest, meta.BundleSHA256) { return "", nil, fmt.Errorf("skill bundle semantic digest mismatch") } } // ... write bundle.json, then fetch and verify files one by one for _, entry := range manifest.Files { if !filepath.IsLocal(filepath.FromSlash(entry.Path)) || strings.Contains(entry.Path, "\\") { return "", nil, fmt.Errorf("invalid bundle resource path") } // ... SKILL.md reuses its body; other files go through io.LimitReader(resp.Body, entry.Size+1) data, err = h.readPackageResource(ctx, resolve(entry.Path), entry.Size) // ... err check omitted sum := sha256.Sum256(data) if int64(len(data)) != entry.Size || !strings.EqualFold(hex.EncodeToString(sum[:]), entry.SHA256) { return "", nil, fmt.Errorf("skill bundle resource digest mismatch: %s", entry.Path) } // ... stage to a temporary staging directory }

Two small details are worth noting. First, hashing bundle.json as raw text is easily tripped up by newlines and indentation, so SemanticDigest() (skill/marketplace/bundle.go:60) extracts four fixed root fields, re-encodes them as deterministic JSON, and then computes SHA-256 — Windows/macOS line-ending differences won't kill a legitimate package, but flip a single bit in any file's path, role, byte count, or hash and the digest fails immediately. Second, the read limit for remote files is entry.Size + 1: reading only entry.Size bytes would silently truncate an oversized response; reading one extra byte means that if the upstream emits any extra data, int64(len(data)) != entry.Size catches it on the spot.

When installing this PDF Skill, InstallFromCatalog can pick a matching factory package or fetch a candidate from the Hub. Both paths enter Marketplace.Install; after file-by-file checks pass, the host-registered BundleValidator checks the templates against the current engine's contract. If validation fails, the old version stays, and a failed candidate download also cleans up the temporary directory. Dependency ordering is a separate flow: after InstallWithDependencies completes its DFS cycle check, it calls Hub.Install item by item for the single-file Markdown entries.

Offline BOM, credential box, and protocol foundation: turning “installable” into “stable offline, secrets sealed, links never blindly fetched”

Once a single package and a single directory bundle are locked down, three of the most easily overlooked system boundaries remain: how the catalog syncs, how secrets are stored, and how multimedia and links returned by the protocol are handled.

First, catalog sync and the offline BOM. In hexclaw/config/defaults.go:4, the default marketplace reference is pinned as const DefaultSkillsHubRef = "v0.1.1". Explicit configuration can override this default. The companion skill/hub/embed.go uses //go:embed to bake index.json and mcp-registry.json — two factory snapshots of about 52 KiB each (about 105 KiB combined), verified byte for byte as identical to hexclaw-hub v0.1.1 — into the binary.

When you open the marketplace, in-memory catalog data is read first. If memory is empty, the default remote marketplace reads a disk cache no older than the factory snapshot, otherwise the embedded catalog is used. The disk cache is partitioned by repository address and reference. While the catalog is fresh enough — 10 minutes — background fetches are skipped. Consecutive background attempts are at least 60 seconds apart, measured from the start of the previous attempt, and at most one background refresh task runs at a time.

In the refresh phase we specifically guard against two kinds of dirty state. If only index.json arrives and mcp-registry.json does not, the call returns RefreshDegradedError and the old catalog keeps serving. When a comparable snapshot from the same source exists, an older candidate reports RefreshStaleError. Different content with the same timestamp, or different content with no timestamp, reports RefreshUnorderedError. On commit, POSIX writes and fsyncs a temporary file, renames it to the final path, then syncs the parent directory. Windows replacement uses MOVEFILE_WRITE_THROUGH. If syncing the POSIX parent directory fails, the code reads back: if the readback matches the candidate, the new snapshot is already in effect and CacheCommitOutcomeError is returned to report that on-disk durability is unconfirmed.

Next, the local credential box. Many MCPs (MySQL, MongoDB, GitHub, Linear, to name a few) need passwords and tokens. Early clients often dropped them into config files in plaintext, or encrypted the whole args array — which also turned legitimate database paths into ciphertext. In hexclaw/config/mcp_secret.go:66-144, credentials follow two tracks: when a secret box (secret.Box) exists, non-empty env values are encrypted at rest, and args encrypts only the parameters explicitly marked by index in ArgsSecretRefs. As soon as a config carries ArgsSecretRefs / EnvSecretRefs metadata, the write path EncryptMCPSecrets refuses to write without a box; the startup decrypt path DecryptMCPSecrets likewise fails closed on any ciphertext or metadata, refusing to continue — it never passes a raw enc:v1:... blob to the child process (a plaintext compatibility boundary is kept only for legacy MCP configs with no secret metadata when writing without a box).

Finally, the underlying MCP protocol foundation. Anthropic's Skills over MCP only works because the client fully supports MCP's Resources primitive, not just Tools. In hexagon v0.6.0 and hexclaw v0.5.2, we wired up all three session types from the official Go MCP SDK — Tools / Resources / Prompts (see hexclaw/mcp/resources.go and prompts.go) — with each resource explicitly bound to Server + URI to avoid name collisions across servers.

More critical is the isolation of multimodal return values. In hexagon/mcp/content_projection.go, images, audio, and binary embedded resources returned by the protocol are stripped into a separate BinaryContent, so hundreds of KB of base64 text don't gum up the model's context; Descriptor() recomputes size and SHA-256 from the bytes actually received rather than trusting upstream declarations. And when a resource_link appears, the source sets a hard red line:

// hexagon/mcp/content_projection.go:38-42, 142-143 (self-computed byte digest + resource link projection) func (b BinaryContent) Descriptor() BinaryDescriptor { hash := sha256.Sum256(b.Data) return BinaryDescriptor{Type: b.Type, Name: b.Name, MIMEType: b.MIMEType, SourceURI: b.SourceURI, Size: int64(len(b.Data)), Digest: "sha256:" + hex.EncodeToString(hash[:])} }
case "resource_link": projection.Text = wire.URI // record only the source URI here

Not blindly fetching links may sound like a minor detail. At this layer, a resource_link is only placed into the returned content as a URI. Whether to access it later, and with what permissions, is a separate decision for the layer that actually makes the call.

An honest note: the boundaries of this version

Having listed the defenses, it's time to lay out plainly what this version has not finished, or what this architecture cannot block by itself, so you don't misjudge its protective ceiling:

  • MCP's remote Skills extension (SEP-2640) is not yet integrated. The HexClaw marketplace pins the Hub release reference by default; the Resources and Prompts already wired up form the basis for future integration. How new versions are discovered, manifests verified, and loading approved still needs to be implemented on the host side.
  • Integrity and dependency_constraint in the catalog are admission declarations, not a lock on the final bytes of every transitive dependency — second- and third-level npm / PyPI dependencies are resolved by the local npx / uvx; whether the runtime installer re-verifies downloaded package bodies byte for byte is a separate execution boundary, and the presence of metadata alone must not be taken as proof that the actually downloaded bytes were checked;
  • Only 1 of the 78 Skills is a directory bundle today (homework-pdf 1.1.8) — the other 77 remain single-file Markdown; the per-file verification and host compatibility chain is working, but ecosystem coverage is nowhere near complete;
  • Pinning and isolation handle marketplace admission. The Agent's tool calls are handled by the host under permission rules. An already running stdio MCP is a host child process; file reads/writes and network access follow the actual deployment's system permissions and isolation settings.
  • Factory snapshots and caches keep the catalog viewable offline, not run every third-party MCP offline — enabling for the first time an external MCP whose package must be fetched with npx or uvx still depends on the local package-manager cache or connectivity to the official registry.

The order ahead is clear: keep watching the evolution of MCP's official Skills extension spec; if remote Skill fetching is ever integrated, the precondition must be content-hash pinning and human confirmation before any change — never silent hot updates. At the same time, migrate more heavyweight Skills with templates, scripts, and Schemas into the bundle.json directory-bundle system, and evaluate fuller local lockfiles and download verification for high-frequency MCPs.

Back to those 10 packages with 404: connecting tools is easy; holding the trust boundary is the real test

Look back at those 10 quarantined 404 entries and the weather service that nearly tore a gap in the door for SDK compatibility: many security risks never reach the level of a zero-day — they start with a casual @latest written in the “just get it running” moment. Once tools bring their own playbooks, the Agent also needs to know which version of the workflow it is using. Pinning the default marketplace reference to a release tag, verifying artifact declarations, and checking directory bundles may look clumsy, but these locks are what make it possible to trust a local machine to an Agent.
